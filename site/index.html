sandcastle-kit

Turn your ticket backlog into a software factory.

sandcastle-kit runs Claude Code agents unattended, one Docker sandbox per ticket. A second agent reviews each branch against its ticket, and only a branch that passes your own lint, tests and build is merged, into your local branch. Nothing is pushed until you push it.

$ git clone https://github.com/henkisdabro/sandcastle-kit.git ~/sandcastle-kit && cd ~/sandcastle-kit && pnpm install && ./bin/sandcastle setup

Start with a dry run Read the source on GitHub

macOS or Linux, Docker (or OrbStack, or Podman), Node 22+, and a Claude subscription or API key.

You already run Claude Code all day. It still needs you in the loop.

      
Someone has to pick the next ticket, start the next session, carry context across and check what came back. For the hard problems that someone should be you. For the well-specified tickets, sandcastle-kit does that part: write them down, mark them ready, start a run, and read what happened in the morning.


      

        

          
It fits if

          
    
            
  • + your work lives in GitHub Issues or Markdown ticket files in the repo;
    • 
            
  • + most tickets are small and closed - a bug, a small feature, a refactor, tests, a dependency bump;
    • 
            
  • + the repo has gates a machine can run: lint, typecheck, tests, a build;
    • 
            
  • + you would rather review a report than watch a terminal.
    • 
          

        

        

          
Not yet if

          
    
            
  • - your tickets say "make it faster" - an agent with no chat context needs a closed spec;
    • 
            
  • - nothing in the repo tests anything, so nothing stands between a guess and your main branch;
    • 
            
  • - you want to pair with an agent live - use Claude Code directly for that;
    • 
            
  • - your tickets live only in Linear or Jira. GitHub Issues and ticket files are the queues today.
    •

How it works

      
    
        
  1. 
          
    Install once
    
          
    ./bin/sandcastle setup puts sandcastle on your PATH, installs the agent skill for Claude Code, Codex and OpenCode, walks you through your tokens and ends with a health check.
    
        
    2. 
        
  2. 
          
    Point it at a project
    
          
    sandcastle init reads your stack and fills in the gate commands for you to check against CI. sandcastle build makes the project's image.
    
        
    3. 
        
  3. 
          
    Queue tickets
    
          
    Label a GitHub issue ready-for-agent, or give a ticket file that status. Ask your agent for /sandcastle queue to tighten the vague ones first.
    
        
    4. 
        
  4. 
          
    Run
    
          
    sandcastle run, or DRY_RUN=1 sandcastle run the first time: implement, review and gate, but never merge or close. Watch it with sandcastle status.
    
        
    5. 
        
  5. 
          
    Land and push
    
          
    sandcastle report prints the summary again. land merges a branch you fixed, requeue sends a ticket back. Then you push.
    
        
    6. 
      

    


    

      
Safe to leave alone

      
Agents run with permission prompts off, inside Docker. The container is the boundary, and the kit narrows what can cross it.

      

        

          
Into the sandbox

          
    
            
  • A token that cannot push. Only a fine-grained GitHub token for issues goes in, and sandcastle doctor --verify checks it cannot push. An empty value is refused, so a host API key cannot leak in.
    • 
            
  • Tickets grant no permissions. A ticket that asks an agent to touch .git/, credentials or a push is not the work, and the guards below hold if an agent tries anyway.
    • 
          

        

        

          
Before a merge

          
    
            
  • Review, then your gates. A second agent reviews every branch against its ticket and fixes what it finds. Then the orchestrator, never the agent, runs your lint, tests and build. Only a green branch merges, and the merged branch is gated again.
    • 
            
  • Risky changes wait. A green branch that touches hooks, CI, agent settings, package-manager config or install scripts is labelled needs-human and left for you.
    • 
          

        

        

          
On your machine

          
    
            
  • Nothing is pushed. Green branches merge into your local base branch. The kit never pushes or deploys; on GitHub it only labels, comments on and closes issues.
    • 
            
  • .git is fingerprinted. If a sandbox changes .git/config, info/ or hooks, the run stops before your machine runs another git command there.
    • 
            
  • Host hooks stay off. During a run your own git calls ignore hooks, so a branch that adds one cannot run it on your machine as it lands.
    • 
          

        

      

    


    

      
Install

      
    
        
  1. 
          
    Install the kit, once per machine:
    
          
    $ git clone https://github.com/henkisdabro/sandcastle-kit.git ~/sandcastle-kit && cd ~/sandcastle-kit && pnpm install && ./bin/sandcastle setup
    
        
    2. 
        
  2. 
          
    Point it at a project:
    
          
    $ cd ~/code/your-project && sandcastle init && sandcastle build
    
        
    3. 
        
  3. 
          
    Mark a couple of tickets ready-for-agent and try a dry run. It implements, reviews and gates them, but never merges or closes a ticket:
    
          
    $ DRY_RUN=1 sandcastle run
    
        
    4. 
      

      
Needs macOS or Linux, Node 22+, pnpm, git, the GitHub CLI signed in (skippable with ticket files) and a container runtime. Full requirements.

    


    

      
Questions

      

        What does it cost to run?
        
The kit is free and MIT-licensed. Agents use your Claude subscription or API key through Claude Code. Every run on your machine shares one plan allowance; the first ticket that hits the usage limit stops that run's queue, and USAGE_CHECK=1 stops it starting tickets before then.

      

      

        Which models does it use?
        
By default Claude Sonnet 5.5 implements and Claude Opus 5.5 reviews. A model: or effort: label changes one ticket, and CROSS_REVIEW=1 adds a third review by an OpenAI model through Codex.

      

      

        Does it push to GitHub?
        
No. Green branches merge into your local base branch and the issue is closed with a comment saying so. You push when you are happy with what landed.

      

      

        Can a run go all night?
        
Yes. A run keeps the machine awake until it ends (caffeinate on macOS, systemd-inhibit on Linux). Closing a MacBook's lid still sleeps it unless it is on power with an external display. With autonomy set, one run re-runs its conflicted and newly unblocked tickets by itself.

      

      

        Do I need Matt Pocock's skills?
        
No, but they help. His /to-tickets and /triage are a good way to write tickets an unattended agent can finish, and the kit reads the tracker and labels his setup skill records.

      

      

        Linear, Jira, Windows?
        
Linear issues can block a ticket today, but the queues are GitHub Issues and Markdown ticket files. The kit runs on macOS and Linux.
