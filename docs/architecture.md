# Architecture notes

What each of the kit's larger modules owns, in more detail than `AGENTS.md`'s Layout table. Read
the section for a file before changing it; update it in the same commit when a rule here changes.
The terms (run record, attempt, ending, requeued) are defined in `CONTEXT.md`.

## `bin/sandcastle`

Shell entry; resolves symlinks, checks the temp directory can be written, runs `src/cli.ts` in one node process with the kit's own tsx loader (not the tsx binary, whose child is SIGKILLed on a slow answer to SIGTERM); `sandcastle herdr ...` runs `src/herdr-plugin.ts` alone, as Herdr's tab bar calls it every 10 seconds

## `src/cli.ts`

Commands: help, `--version`, setup, doctor, init, updated, build, gates, land, preview, lean, lean-apply (internal hook), preflight, queue, requeue, blockers, run (`--detach`), wait, stop, report, status, clean, herdr; also the autonomy loop around `burndown()`. The help text and each command's `--help` come from `src/help.ts`

## `src/burndown.ts`

The orchestrator: base gates, then every attempt and landing through `createSchedule(plan).run(work)` (the attempt port: implement, review, gate with repair, in the pipeline `createPipeline(ctx)` makes; the land port: merge or squash, on the landing worker as each ticket goes green), then verify and report; it records what the scheduler tells, handing each ending to the ledger (`src/ledger.ts`), and posts the hold notes and the comments the ledger words after the schedule; the attempt reports its pipeline (`attempted`) with the agent's hand-back read as it ends (`handBack`) and the `.git` check after its sandbox closed (`settleAfter`), whose failure stops the run without replacing the pipeline's own ending, and writes only the pipeline's facts (commits, minutes, tokens); dependencies, the files the scheduler's hold compares (`ticketFiles`, `refreshFiles`: one ticket at a time per file git cannot merge) and the record of what it tells (`createHoldRecord`), re-runs of carried branches (land-only, narrow review), timings

The pipeline takes everything outside itself through one `PipelineContext`, as a landing takes its `LandContext`: its sandbox (`open`, whose `run` is every agent pass and `exec` every git command in it), its gate runs (`gate`), the step timer (`timed`), and what the run keeps across a ticket's attempts (`requeuedAs`, `results`, `reds`, the heads record under the project root). `test/pipeline.test.ts` drives it over a temp repo with a worktree for the sandbox, scripted agents and scripted gate runs: a change to the pipeline is tested there, by what it does, not by matching the source of `src/burndown.ts`.

## `src/landing.ts`

`landOne(ctx, outcome)`: landing one green branch (tracker check, moved head, held paths, then a merge as it is when the branch holds the base's tip, otherwise a merge gated in a sandbox, close) and what it returns - how it landed and the facts the run record keeps (the files a conflict or hold names, a red tree's failing tests, the paths beyond the Touches line, a failed close's error) - writing no verdict of its own, only the `landing` stage; `landingWork(ctx)`: the scheduler's land and host ports over one `LandContext`; the lines of a requeued ticket; `createHostGit`: the mutex through which every host git write goes and which moves the run's expected base; also the landing merge, its abort and the conflict line. What it posts to the tracker as it lands (the close comment, a hold, an earlier merge closed) it asks the ledger's `describe` for

## `src/ledger.ts`

The ticket ledger: one place that turns each ending (`src/schedule.ts`) into everything a run says about its ticket.

- **`describe(ending, context)`** is pure and exhaustive over the `Ending` kinds (the type checker holds it): the ticket state the run ends on, the **outcome** (kind, `with`, text), the view's word and whether it counts as landed, and the tracker's text (a close, a hold, or the one comment on a ticket that did not land). The context is what the ending does not carry: the base, the gates' names, the agents' report, a dry run, a kept worktree, a hold note (the ticket gets that note, never a second comment), the run's stop line. The agent's hand-back through the tracker's hold label is on the pipeline's result (`handedBack`), so the ending arrives complete. `test/ledger.test.ts` holds every ending's four sayings side by side.
- **The writer** (`createLedger`) records what `describe` says as burndown's `tell` hands it each ending (`ledger.tell`): the ticket state the run ends on, the outcome and the view's word - it is the only writer of each, so neither `landOne`, the attempt nor the burndown after the schedule writes a verdict. Its `outcomes` port is `outcomesFile`, the one caller of `recordOutcomes`. `test/ledger-guard.test.ts` holds that: outside `src/ledger.ts` a run writes only progress - a phase, the landing stage, queued or blocked, a note, the pipeline's facts - spelt out in each `.ticket(...)` call, and nothing calls `recordOutcomes`. Each ending is recorded once, as it is told; a ticket the run's stop left unstarted waits for the run's last words (`close(endings, stopLine)`, after the schedule: the most severe cause, which a ticket told earlier could not know). Beside the endings, `ready` writes a green branch as it waits to land, with its outcome and what will hold it for a person at landing. Each ticket's entry is kept.
- **A requeue** is a told change the writer records: the ticket written as queued with the line its second attempt's setup carries (`requeuedAs`), before it is pushed back. A second collision's note names the tickets of both attempts (`describe`). `landOne` writes no verdict, so a requeued ticket whose second attempt never began has nothing to undo: it is recorded from the ending the scheduler makes of it (its first landing, or withdrawn - then said as not started, and its first pipeline's line dropped), its record no longer `requeued`. `test/landing-requeue.test.ts` drives the scheduler with this writer over fake ports.
- **`accountLanding(entries)`**: what the closing notification and the verify read - the merged list and the counts - from the entries.
- **`partly-done`** is a landing ending: a branch an agent said leaves an acceptance criterion undone (its `<unmet>` line, read by `unmetOf` as `ungatedOf` reads `<ungated>`; the reviewers' word replaces the implementer's once a full review ran) merges, but the ticket is neither closed nor released to its dependants, and the ledger's comment names the criterion. Its merge subject says `part of` the ticket, not `closes` it (`mergeSubject`), so `mergedEarlier` does not close it on the next run, which picks up the remainder while the ticket stays queued (`Facts.partial`, read from the tracker by `gather`; `partialRerunnable` makes it re-runnable for the autonomy loop, and `drainStop` stops a drain that leaves the same ticket partly done twice). An `<unmet>` line that `needsDecision` reads as a person's decision is not re-runnable: the ledger comment and the report suggest the hold label instead.
- Also the words themselves: `closeComment`, `partlyDoneComment`, `notLandedComment`, `pipelineOutcome`, `refusedRecord`, `withdrawnRecord`.

## `src/resolution.ts`

`strayChanges`: compares a conflict resolution with git's own automatic merge (`git merge-tree --write-tree`, git 2.38 or newer) and names the changed paths that merged cleanly, so the land-only path holds the ticket instead of reviewing a resolution that dropped another ticket's lines

## `src/schedule.ts`

`createSchedule(plan)` is the run's one path for attempts and landings: `start` (the candidates in
start order) and `run(work)`, which resolves to each ticket's typed **ending** and the run's stop
state.

- **Ports.** `attempt` (with `last()`, true once nothing more will start), `land`, `host` and `tell`.
- **Requeue once.** A first conflict or red at landing gets a second attempt carrying what it
  collided with, unless the run starts nothing. The ticket is told before it is pushed back; a
  second collision is final. A red one is repaired from the landing gate's own output, with no gate
  run, when the requeue's merge joins the base tip and branch head that gate ran on
  (`repairFromRed`, `src/landing.ts`); on a moved base the gates run first.
- **Release of dependants.** The tickets held for a blocker that starts in this run: when one lands
  and closes, the blockers of the ones that waited for it are read again through the plan's
  `blockers.open` port, and each with none open starts through the file hold. Any other ending, a
  run that starts nothing or a dry run releases none, and each held ticket is told what it waits
  for now.
- **Endings.** The queues stay open until every ticket has its ending; on each ending its files are
  freed and its dependants released before the open count drops.
- **The file hold** (the scheduler's own too). A ticket sharing a file git cannot merge with one in
  flight is parked until that one lands or leaves the run. It is decided for the start as the
  schedule is made (`start`: the candidates in start order, each with its wait, before the run
  record exists) and told as the run goes (`started`, `waits`, `next run`). Mergeable shares are
  only named. A ticket in flight has its branch's files read again before each comparison; a run
  that starts nothing tells each parked ticket it waits for the next run; a dry run (no `files`)
  holds nothing.
- `createStopState`: the stop state, whose `add` only the scheduler holds.
- `createLanding`: the one worker that lands each green ticket, a carried branch first.
- `createQueue<T>(rank?)`: the work queue of the pipeline fan-out and of the landing worker (`push`,
  `close`, `run(workers, fn)`). Workers wait while it is open and empty, so an item can be pushed
  mid-run; a higher `rank` goes first, equals in arrival order.

## `src/upgrading.ts`

Whether a pulled kit has **Upgrading** notes a project has not had: the project's update record (`.sandcastle/.run/kit-updated`, written by `sandcastle updated` and `init`: the release and the notes acted on; an older record's kit commit is read through git) against the kit's own notes, and the lines doctor and a run print. Also `kitVersion`, the version doctor and `--version` print: `package.json`'s release, and in a clone past its tag, the distance and commit

## `src/herdr.ts`

Herdr helpers and the run's view: the tab (adopted only from a terminal), per-sandbox panes only with `herdr.panes: "all"` (otherwise the run is one agent on the status pane), agent-state reports, sidebar tokens, the workspace's run summary. `reportInDeadTab(root)` is for a run that is no longer live: Herdr's cold restart leaves its tab as idle shells, so the status pane of the tab the kit opened (`herdr-view.json`: `adopted` false, the pane still in the recorded tab, and a bare shell by Herdr's process info (`runsBareShell`: one foreground process, a known shell, at most login or interactive flags) - never the status view, an editor, `claude` or a REPL) runs `sandcastle report`, and the record is marked `reported` so it is shown once. Two callers cannot both type it: the record is claimed by renaming it to a name of the caller's own before anything is typed, and written back marked (or unmarked, if herdr failed) afterwards. An adopted tab is a person's terminal and is never touched. `liveRuns` in `src/herdr-plugin.ts` calls it (`tellDeadTab`) for each run file whose record says finished or dead (the tab bar's tick, and the actions' project lookup: the first reader to drop the file tells the tab). The tab bar's command runs the kit only while the runs directory has a file, so a dead run's file is kept while its view record (`adopted` false, not `reported`) names a status pane in the recorded tab whose foreground still runs the status view (`runsStatus`): a kill followed some time later by a restart, or by the view being quit, is reported on the first tick that finds the pane a bare shell. In every other case - the report typed, the record `reported` or `adopted`, no record or no status pane, the pane gone or in another tab, anything else in it, any herdr error - the file goes. Before removing it the reader reads the project's `run.json` again and leaves the file if that changed since it judged the run dead: the file is named by the project, so a new run of it registers under the same name. A run that ended cleanly removes its own file, so its tab is left as it is by a later restart

## `src/live-runs.ts`

The machine-wide live-runs directory (`RUNS_DIR`, in `KIT_CACHE`: `sandcastle-kit` under `XDG_CACHE_HOME` or `~/.cache`, on Linux and macOS alike): `registerRun` writes a run's file (named by the resolved root) from `burndown()`, Herdr or not, and removes it at exit. The Herdr tab bar (`liveRuns` in `src/herdr-plugin.ts`) and the Claude Code mod (`REGISTRY_SCRIPT` in `mod/hooks/run-state.ts`) read it; the mod follows a run whose recorded `session` (`CLAUDE_CODE_SESSION_ID`) is its own. `commandOf` is the real process check that `liveness` is given: a signal of 0, then `ps -p <pid> -o command=`. `PLUGIN_MARKER` (`herdr-plugin-linked`, beside it) is left by `sandcastle herdr configure` and removed by `--remove`; `status.sh` reads it once at start-up (inside Herdr, on a terminal) to decide whether to emit ticket links and the `ctrl-click a ticket for its log` hint, as a Ctrl-click does nothing without the plugin.

## `src/blockers.ts`

What holds a ticket back: `Blocked by` refs (GitHub, Linear, ticket files), and comments a run would ignore; `openBlockersNow`: the scheduler's blockers port, the open blockers of the tickets held for one that has just landed; `blockedNote`: the wording of what a held ticket waits for

## `src/touches.ts`

The `Touches:` line of a ticket body: `parseTouches`, `expandTouches` against a ref's tree, and `unmergeableFiles` (lockfiles, `generated` paths, minified blobs; sizes from one cached `ls-tree` per commit), and `isTestPath` (conventional test names; a test file a branch adds is not a `Touches:` overrun, and `overrunPaths` (`src/report.ts`) folds the modified ones into a count, "+7 test files"), `isDocPath` (any `*.md`, and `docs/` and `skill/`: the docs a repo's rules have every change edit, folded by `overrunPaths` into "+2 docs files", so the listed paths are the source files a ticket missed; the close comment says "changed beyond its Touches line: ...", the report "<title> - beyond Touches: ..."), and `isAgentDoc` (`AGENTS.md` and `CLAUDE.md` at any depth; a change to one is not an overrun when the branch adds a file). `touchesOverrun` (`src/landing.ts`) also leaves out a file only a repair pass or a merge commit (a conflict resolution) changed: the repair commits are recorded as `repaired` in the ticket's head record (`heads.json`), across attempts. An overrun of only test and docs files stays in the run record, and `overrunNoted` (`src/report.ts`) keeps it out of the close comment and the report. A scheduling hint and warning source, never a guard

## `src/lint.ts`

`lintQueue()`: the queue's shape for `sandcastle queue --lint` - longest `Blocked by` chain, edges that only order overlapping `Touches:`, wide tickets, hot and shared unmergeable files, tickets whose `Touches:` names a protected path (always held), `blockerProblems` and blockers listed under a heading (which the parser does not read), a rough estimate. Read-only advice

## `src/detach.ts`

`sandcastle run --detach`, `wait` and `stop`: `startDetached` (the run as a process of its own - `spawn` with `detached: true`, output to `.sandcastle/logs/run-output.log` - and the line printed once it is going), `livePid` (the run lock's pid, if it is a process of the kit), `waitForRun` (also waits for the pid run.json names while it has no end, and the one it last saw, to die: the lock goes before the record's `exitCode` is written), `recordedExitCode`

## `src/guard.ts`

Host safety: git hooks and auto-gc off, command-running config pinned, `.git` fingerprint (config, HEAD, info, hooks; its base is the one the run expects, which the landing worker moves only by its own writes; and the tips of `agent/issue-*`, which `HostGit.begin`, `settle` and `forget` in `src/landing.ts` keep: a ticket in flight may move its branch, any other tip that moves stops the run, and a branch that vanished is restored from the bare repo `.sandcastle/backup.git`, where a pipeline's end copies it, with the base branch under `refs/base` so a fetch is thin, and a landing drops it and, with no agent branch left, runs `gc --prune=now` in the backup alone, whose git calls turn background maintenance and cruft packs off so the prune is never refused by a detached auto gc), a deleted or moved base stops with the `update-ref` that restores it, a worktree record rewritten to a container path is named, protected paths and files over 50 MB held for a person, run lock

## `src/pool.ts`

The machine pool: sandbox and gate slots shared by every run on the machine, and the lock-file helper the run lock shares (`takeLock`: pid and token, guarded takeover). A **slot** is a lock file `<pool>-<n>.lock` whose line reads `<pid> <token> run=<id> <label>`: the pid stays first because `status.sh` reads it, and `run=` names the holding run (`RUN_ID`, one per process) so `slotsByRun` can count slots per live run. A lock from a kit that named no run reads as a run of its own pid.

A freed slot goes to the **longest wait, across runs**. `withSlot` writes a wait entry (`waits/<pool>-<since>-<run>-<n>.wait`, `<pid> <run> <since> <label>`, renamed into place whole) before its first try, and takes a free slot only when no other live run has an older entry for that pool (ties go to the lower run id), then removes the entry. Without it the run that has just freed a slot asks again at once and almost always wins, and a second project's run waits until the first drains. The rule is per pool, so a run holding a sandbox slot and waiting for a gates slot cannot deadlock on it. Waits of one run are never ordered against each other here: `slotTurn` (`src/landing.ts`) still puts a landing before the run's next pipeline. A wait entry or slot whose process is gone (`holderRunning`, the run lock's rule) is ignored, a wait entry's removed when seen, a slot taken over by the next `takeLock`. A younger waiter does not take a free slot while an older one polls (every 5 s), so a freed slot can idle up to one poll. A run started by an older kit writes no entries and is not waited for.

**Shares** (`docs/adr/0001`): live runs split the sandbox pool equally, up to each run's demand. A run registers with `joinPool` (`burndown()`, once per process: an autonomy run's next turn updates it) in `runs/<run>.run`, a JSON line written whole and renamed in: `pid`, `run`, `project`, `demand`, `concurrency`, `since` and `shares: true`, the mark of a kit that knows them. A registration whose process is gone (`holderRunning`) is ignored and removed when seen, and the file goes with its process. `members()` lists every live run that is registered or holds a sandbox slot, with its share: `splitShares` divides the limit equally among the runs whose demand is above 0, a run that needs less than an equal part releasing the rest to the others, again equally, in whole slots (the earlier registration gets the odd one, so every run works out the same split from the same files). A run with slots and no registration is from an older kit (or a command that is no run): it is counted as wanting its concurrency, read from the run record that the live-runs directory and the record's `pid` lead to, or the slots it holds if that cannot be read, and takes no share on trust. The share is taken by `withSlot("sandboxes")` of a registered process only: a run at or above its share (`held` counts) takes no slot while another run below its share wants one - a registered run below its share does, whether or not it has a wait entry at that instant (its demand is what it asks for next, so a run between two of its tickets is not mistaken for one that wants nothing), and any other run does with a wait entry - and with no one wanting one a free slot is taken as before. The wait order skips waiters that are at or above their share, which cannot take a slot, so an older wait of such a run never idles a slot. A slot held is never taken back. The check and the take are one synchronous step, so a run's own waiters cannot both pass it. `withSlot`'s `onWait` is told why a wait waits (`slots` or `share`, again when it changes), and `myShare` reads this run's demand, share and held slots. The gates pool has no shares. `inject` (`src/pool.ts`) replaces the pool's process check and clock, so `test/pool-sim.ts` can drive one run in the test's own process against other runs written as files (registrations, slot locks, wait entries) with a short poll: `test/pool-shares.test.ts` and `test/pool-cap.test.ts` run in about 2 s, where child processes polling in real time took 10-66 s a test under load. A registration going with its process, and the cap in it, is the one thing they still start a process for.

**Measured peaks** (`src/peaks.ts`, read by `src/size.ts`): `sandcastle size` sizes `maxSandboxes` from what sandboxes used, not an assumed figure. `samplePeak` runs `cat /sys/fs/cgroup/memory.peak` through the sandbox's own `exec` (cgroup v2's high-water mark in bytes; no host-side `docker stats`, no container naming) after each `runGates` pass, which puts the largest reading so far on the `GateRun` as `peakMib` (a green `requireGreenBase` returns it too) - `timed()` in `src/burndown.ts` copies it to that step's `timings.jsonl` line, which `typicalTimes` and `estimate` never read - and `recordPeak` reads once more just before the sandbox closes (a pipeline's `finally`, and `gateBase` for the base and verify gates) and appends one `{ts, project, run, peakMib}` line to `peaks.jsonl` in `KIT_CACHE`, beside `runs/` because that directory's files go when a run ends. The largest reading of a sandbox is kept in a `WeakMap` keyed by the sandbox. `project` is `projectId(root)`, a 12-character hash of the resolved root, and `run` the run's start time: no path or name is written (`test/peaks.test.ts` holds it), and a run is the lines that share `run`. Everything is best effort: a missing file, a failed or 10-second-late read or an unwritable cache records nothing and never fails a pass. Landing sandboxes (`src/landing.ts`) are not read. `measuredPeak(peaks, now)` is the rule, pure: each project's highest peak over its last 5 runs (`RECENT_RUNS`), the highest across projects whose newest run is within 30 days (`FRESH_DAYS`), plus 10% (`MARGIN`); `recommend(memory, cpus, peaks, now)` uses it in place of `PER_SANDBOX_GIB`, and with nothing measured keeps the assumed figure, which the output says. The gate limit keeps its CPU rule, and shares divide whatever limit is set.

**The cap** (`sandcastle cap`, `parseCapArgs`, `setCap` and `standing` in `src/pool.ts`; the command in `src/cli.ts`, which handles it before the repository check so `--project <name>` works from any directory): a person's limit on one live run's share, the optional `cap` field of that run's registration, so it ends with the run (a new run has a new registration, and an autonomy run's next turn is the same run and keeps it). `cap N` writes it, `cap off` removes it, a bare `cap` reads `standing()`. The run is found by the `project` its registration records, so the name is `loadProject`'s `name`; no live run, or two of one name, is a refusal, and so is a number above the registration's `concurrency` (the most a run ever wants) or anything that is not a whole number of 1 or more. The cap is written whole and renamed in, like the registration, and the run reads it as `members()` reads every registration, before each slot request. `splitShares` takes each run's demand as the smaller of its demand and its cap, so a cap only lowers a share and what it frees goes to the others up to their demand. `overShare` adds one rule: a run that holds its cap takes no slot even when no other run wants one (held, not share: with a demand below the cap the share is below it too, and a run with no rival takes slots past its share). Nothing is taken back: a run above its cap keeps its slots. The cap is a person's and written from another process, so the run's own copy of its registration never holds one: `writeRegistration` (a new demand) reads the cap from the file and keeps it. A cap set in the instant the run rewrites its registration can be lost - the person sees the cap missing in the next read-out and sets it again. The run record carries `cap` beside `demand` and `share` (`burndown()` rewrites all three when any changes, a lifted cap leaving the record); the status view's machine cell appends `· cap N`, and the Herdr tab bar line shows each run's `share` from its record.

The start line (`burndown()`, before the estimate): `otherRuns()` lists the live runs other than this one that hold or want a sandbox slot, `splitAtStart(demand, others)` works out the share this run would get beside them and how many slots are free this moment, and `startLines(split, neighbours)` words it - each registered run's project, slots and demand, this run's share, and when no slot is free the wait for the first (`firstSlotWait` in `src/run.ts`: the other project's `typicalTimes().issue` less its working tickets' ages, a minute at least, found through `recordOfRun(pid)`, the live-runs directory and the run record's `started`; left out with no history). A run with slots and no registration gets a line of its own that says it predates shares; the run still starts. No other run: no line. The estimate's divisor is `estimateSlots(workers, split)`: the workers within the run's share when another run is live, else within the machine limit (`test/start-split.test.ts`). `estimate` also takes `limit("gates")` as `detail.gateSlots`: each history ticket's summed `gates` and `landing gates` line time (the wait is `waitMs`, outside `ms`) over those slots is a third bound beside the sandbox rounds and the chain, and the largest sets the time (`test/estimate-gates.test.ts`). A landing gate writes a line of its own phase (`LANDING_GATES`, `timedLandingGate` in `src/gates.ts`, wrapped round the landing port in `burndown()`), which `typicalTimes` and `estimate` keep out of a ticket's own pipeline time. The landings in a row (the history tickets' landing gates, none for one that landed without a gate, summed over the run's tickets: one worker, whatever the slots) are a fourth bound, a floor on the end, and the estimate says when they set it. `typicalTimes` carries the same figure as `typical["landing gates"]` (the median ticket's landing gates, in seconds), from which `status.sh` takes the later of the pipelines' end and now plus the tickets not yet landed times that figure for `ends ~HH:MM` (`test/landing-gate-timing.test.ts`).

The demand comes from the scheduler (`src/schedule.ts`): the tickets from their push to the pipelines to the end of their attempt, plus one while a green branch waits to land or is landing, never more than `work.concurrency`, told as `{ kind: "demand" }` whenever it changes; `burndown()` hands it to `setDemand`. A ticket held for a blocker or a file adds nothing until it starts. The base gates (before the scheduler) and the verify run ask for one slot. Workers still start up to the smaller of concurrency and the machine limit: the share decides how many hold a slot.

## `src/usage.ts`

The opt-in plan usage guard (`USAGE_CHECK=1`). `usageToken(env, platform, readers, now)` is the one function that picks what a reading is made with, and `LoginReaders` (`keychain()`, `file()`) are injected so a test needs no real keychain. The guard applies only while the sandboxes spend a subscription token: `usageToken` returns `{ source: "api key" }` (the start line says the guard does not apply, no reading, no stop) whenever `ANTHROPIC_API_KEY` is set, beside `CLAUDE_CODE_OAUTH_TOKEN` or not, and `undefined` with neither, and in neither case reads the host login; a key wins over a token, as in `credentialSource`, because Claude Code spends the key first (`src/api-key.ts` then has the run ask before it bills API credits). `usageWhose` words whose plan a reading is of (the login's account, or the token's), for the start line and `doctor --verify`; the kit cannot tell whether login and token are one account. The credential, then, is the host's Claude Code login: on macOS the keychain generic password `Claude Code-credentials` (`security find-generic-password -s ... -w`), or with `CLAUDE_CONFIG_DIR` set `Claude Code-credentials-<h>`, `<h>` the first 8 hex characters of the SHA-256 of its value with a trailing slash removed (`keychainService`), as Claude Code itself names it, elsewhere `.credentials.json` under `CLAUDE_CONFIG_DIR` (else `~/.claude`); the JSON's `claudeAiOauth.accessToken` and `expiresAt` (milliseconds) are what is read. A `claude setup-token` token is inference-only and the usage endpoint answers it HTTP 403; the login's access token carries `user:profile` and gets 200. Rules it keeps: it reads on the host only, in the orchestrator, at each usage reading (`usageLine`, `usageStop`), and never refreshes (a refresh rotates the token and could sign Claude Code out), so the login's own expiry (about 8 hours) ends it - an expired login is "no reading" (fail open, asked again before the next ticket) and does not fall back, since the setup token would only get the 403 that turns the guard off for the run; a missing or unreadable login (no entry, a reader that throws, malformed JSON, no access token) falls back to `CLAUDE_CODE_OAUTH_TOKEN`; the token is never written, never added to the env the run holds, never in `sandboxEnv` or `sandboxMounts` (`src/sandbox.ts`) and never printed - `sandcastle doctor --verify` reports which source the guard would use, where it looks for the login (`loginLocation`: the keychain service's name or the credentials file's path) and the endpoint's HTTP status only. `test/usage-login.test.ts`, `test/usage-plan-applies.test.ts` and `test/usage-keychain-service.test.ts` hold it.

## `src/run.ts`

Preconditions, run arguments, keep-awake, preflight, prompt rendering, agent logs (with the raw `.jsonl` sidecar), run record and history, typical times and the estimate, recorded heads, outcomes (`outcomes.json`: each entry's kind from the closed set, the tickets it collided with and its line; a reader decides on the kind, never the line, and `test/outcome-kinds.test.ts` fails on one that matches the line; `test/status-contract.test.ts` holds `status.sh`'s `outcome_state` to the kinds, both ways), log archive, status pane

The run record's `settings` group (`RunSettings` in `mod/hooks/run-record.ts`) holds the run's settings as one turn wrote them: `autonomy` (the level, resolved once per run), `turn` (this record's, 1-based), `cap` (the level's most turns: 1 for level 0, the level for 2 and 3, `DRAIN_CAP` for `drain`, and none for level 1, which asks after every turn), `repair` (the attempts a ticket gets after a red gate, 0 for off), `concurrency` with `asked` (the tickets at once the run takes after the machine-wide sandbox cap, and the value `--concurrency`, `CONCURRENCY` or the config asked for; the view adds `(asked N)` only when they differ), and `crossReview` (on or off, resolved once per run) with `crossReviewModel` and `crossReviewEffort`, written only when it is on, and the usage guard: `usageGuard` (was `USAGE_CHECK=1` asked for), `usageStop` (its threshold, only while it is on) and `usageReading`. The reading is a fact beside the setting, never a change to it: `unavailable` when the guard's last attempt got none (`usageReadingLost()` in `src/usage.ts`: a 403, a rate limit, no token or an expired Claude Code login), written by `burndown()` after the start line and after each ticket's check, and cleared when a reading comes back - the only settings field that changes during a turn. A record without the guard's fields shows nothing about it. The cap is `poolLimit` in `src/pool.ts`, the pure form of `limit`, over the resolver's own environment and machine settings; effective concurrency is before the ticket count, so a short queue is not drawn as a clamp. The run record's top-level `concurrency` (the sandboxes at once, after the ticket count) is separate and still feeds the view's ETA and free-slot maths. The row shows `repair 1` or, greyed and dropped below 80 columns, `○ repair`, `concurrency 4` or `concurrency 6 (asked 8)`, and `● cross-review <model> <effort>` or, greyed and dropped below 80 columns, `○ cross-review`, and `● usage-guard 90%` or `○ usage-guard` (greyed, dropped below 80 columns; with no reading, `● usage-guard 90% (no reading - not guarding)` in the warning colour, which never drops); for a record that carries `crossReview`, `status.sh` drops the `cross-review` part of the models string so the models cell holds only models, and an older record's string is shown as written. `burndown()` writes it when `cli.ts` hands it a turn, and each turn's fresh record carries its own `turn`. Beside `settings`, the record keeps two live values, `demand` and `share` (the run's demand for sandbox slots and its share of the machine pool, `src/pool.ts`): `burndown()` rewrites them whenever either changes (a demand told by the scheduler, or a share that moved as another run began or ended, read every 5 seconds; the timer stops once the record is finished, `finished`), and they are no run setting, so they are not in the group. The status view's machine cell shows them as `this run  wants 4 · share 3` (with a cap, `wants 4 · share 2 · cap 2`) while the run is live (the gates queue moves to the gates row then), and a queued ticket whose note is `waits for the run's share` shows it as its activity; an older kit's record has neither, and the view then draws the cell as before. The status view's settings row reads only these fields (`test/status-contract.test.ts` holds that), draws nothing from a record without the group, and never fills a field the record lacks. Idle, `sandcastle status` resolves the next run's settings with the same resolver and passes the group as `SANDCASTLE_SETTINGS` (`{}` when they cannot be resolved), with the whole row prefixed `next run:` (an ended run's report holds the settings it recorded, which this row is not); a bare `status.sh` falls back to the last run's record, marked `(last run)`. `status.sh`'s `settings_row` is a list of items, each with its text, a shorter text below 100 columns and the narrowest pane it stays in, so a later setting is one `set_item` call; items that do not fit the pane wrap whole onto further lines (`wrap_items`), so none is cut off.

## `src/run-settings.ts`

The run settings (CONTEXT.md): `resolveSettings({ env, project, machine })`, the one pure resolver of what a run is told at its start - the autonomy level, cross-review (`crossReviewSetting` in `src/agents.ts`: `CROSS_REVIEW=1`, `CROSS_REVIEW_MODEL`, `CROSS_REVIEW_EFFORT`, the same reading `agents.ts` itself uses), the repair attempts, concurrency (asked and effective) and the usage guard (`USAGE_CHECK=1`, with its `USAGE_STOP` threshold, read through `parseUsageStop` in `src/usage.ts` and refused when bad only while the guard is on), with the unchanged precedence of environment over project config over default - and `settingsGroup`, the group a turn's run record carries. `sandcastle run` and `sandcastle status` both call it, so they cannot disagree about the next run; a later setting adds a field here. `test/run-settings.test.ts`, `test/run-settings-repair-concurrency.test.ts` and `test/run-settings-cross-review.test.ts` hold it

## `container/`

Mounted read-only at `/etc/claude-code` in every sandbox (`sandboxMounts` in `src/sandbox.ts`): `managed-settings.json` registers `git-guard.sh`, a `PreToolUse` hook on the Bash, Write and Edit tools that refuses commands and writes that damage the shared `.git` (`test/git-guard.test.ts`). Managed settings sit above project settings, so a branch cannot disable it. Needs bash and `jq` in the image.

The same file carries `permissions.deny` for `Monitor`, `ScheduleWakeup`, `CronCreate`, `CronDelete`, `CronList` and `RemoteTrigger` (`test/managed-settings-deny.test.ts`). A sandbox agent otherwise has Claude Code's whole tool set, and these are the ones that let it wait: a run once held a backgrounded suite for tens of minutes with `Monitor` ticks, doubling its tokens and loading the machine's shared gate slots for every other sandbox. The agent's turn is the unit of work here, so a pass that starts something long ends its turn and says what is still running; nothing in a sandbox schedules a later wake-up, a recurring job or a remote run. Sandboxes run with permission prompts off (`--dangerously-skip-permissions`); a deny rule is checked before that mode and, as managed settings, outranks a branch's own settings, so it holds there. A new tool a sandbox should not have goes in this list, not in the prompts alone.

## `skill/`

The skill serves three harnesses. The directory (not the file - `src/setup.ts` links the directory) is symlinked into `~/.claude/skills/sandcastle` (Claude Code, also scanned by OpenCode) and `~/.agents/skills/sandcastle` (Codex). `SKILL.md` works in all three because each ignores frontmatter it does not know. Keep it portable:

- `name` stays `sandcastle`, matching the directory the user links it as.
- `description` stays under 1,024 characters (OpenCode rejects longer) and carries every trigger: Codex and OpenCode never see Claude Code's `when_to_use`.
- `argument-hint` and `arguments: [action]` are Claude Code's; the body handles an unfilled `$action` for the other two.
- Name harness-specific tools by what they do, with the Claude Code name as an example ("the harness's question tool (`AskUserQuestion` in Claude Code)").
- `SKILL.md` loads whole for every action, so it stays a router: each action's steps live in a sibling file that `SKILL.md` names in prose, and reference two actions share lives once, in the file of the action that owns it (queue.md's "Writing a ticket body") ("read run.md in this skill's directory") - Codex and OpenCode do not fill `$action`, so they find the file from the text.

## `mod/`

The optional Claude Code mod, a plugin linked as `~/.claude/skills/sandcastle-mod`: `hooks/register.tsx` (the hooks: watch `run.json`, the band above the prompt, the needs-you line and notice, the prompt when the run's process is gone, `/sandcastle-status`, `/sandcastle-mark`), `hooks/run-live.ts` (pure, imports nothing: the one rule for "is this run live" - a run is live when its record has not finished and its pid is a process whose command line contains `RUN_COMMAND`; `liveness` answers `live`, `finished` (with its exit code), `own` (the asking process itself, which is not "another live run") or `dead` from the record, the run lock's pid and an injected process check, and EPERM is the check's business: a process that exists is read like any other. `src/report.ts`, `src/herdr-plugin.ts` and `src/detach.ts` pass `commandOf` from `src/live-runs.ts`; the mod passes `ps`; `status.sh` keeps a bash `run_alive` of the same rule, which `test/run-live-contract.test.ts` holds to it. The mod alone ignores `finishedAt`, since every turn of one run writes one and the run goes on; the run lock and the machine-wide slot locks in `src/pool.ts` judge their owner by the same command-line check (`holderRunning`), with one difference: when `ps` cannot answer for a pid that exists, the lock is kept, since a live run misread as gone would let a second one take its project; `status.sh`'s `slot_alive` follows it), `hooks/run-record.ts` (pure, imports nothing: the run record and ticket record types, the closed list of ticket states, the derived states, the tables from ticket state to group and word, and the closed list of outcome kinds; the kit's own `src/` imports it too, so every write is typed by it, `readTickets` passes each state read from disk through the guard, and `readOutcomes` (`src/run.ts`) each outcome kind through `isOutcomeKind`), and `hooks/run-state.ts` (pure: the record read as groups, glyphs and colours, the palette and castle, and the band cut to its width - `test/mod.test.ts` holds both to `src/run.ts` and `status.sh`) and `hooks/idle.ts` (pure, imports nothing: the idle mark, one row of sand above the prompt between runs in a set-up project. `markText(input)` is the line or undefined to clear it; its one input object is the set-up flag, the machine switch, the project's hidden flag, the dismissed ids, the cache `Entry` and the time. `sandcastle · N ready - /sandcastle run` shows N only while the last good read is under `COUNT_MS` (an hour) old, else the bare mark. The ready count: `readyIds(stdout)` takes `sandcastle queue --json` and returns the ids with an empty `blockedOn`, or undefined for anything that is not a list of such tickets (a failed read, never 0); `due(entry, now, trigger)` says to read when there is no entry, the last attempt (`tried`) is `READ_MS` (10 minutes) old or more, or a trigger fired (`run-ended`: a run of the session root's project, or one the session followed elsewhere - perhaps a second clone burning down the same tracker - was seen to end; `skill`: the sandcastle skill was used, and again when the turn that used it ends - its `turn.complete` hook, counting the main thread's turn and never a subagent's - since triaging labels tickets long after the skill starts) - a session's start needs none, its first look applies the age rule at once; `afterRead` makes the next entry, and a failed read keeps the last good `ids` and `at` and moves only `tried`, so a tracker that cannot be reached is tried every 10 minutes, not at every look; `parseEntry` checks what the shared store holds. In `register.tsx` the entry is one `$.store` key per project root (`ready:<root>`, apart from the session entry under the bare root), shared by every session on the machine; at most one tracker read per project every 10 minutes while nothing changes. The idle look reads the entry and the clock and starts `refresh` unawaited - never inside a render hook, and a look never waits for it - so a slow or hung tracker holds nothing up, and the count a read brings shows at the next look (15 s). `refresh` runs one read at a time per session (a trigger that fires during one earns one more read after it; a look that is merely due again does not), `$.process.run` with a 20 s timeout in the project root, the kit's own `bin/sandcastle` beside the mod's resolved folder when it is a plain file there, else the `sandcastle` on PATH. Two sessions racing to one stale entry may both read, which is accepted. Set up is `.sandcastle/config.ts` being a plain file, one `stat` on the 15 s idle look, never `sandcastle doctor`; the switch is `"idleMark": false` in the personal `config.json`, read through `SETTINGS_SCRIPT` with `XDG_CONFIG_HOME` honoured as `USER_CONFIG` is, and never written - `machineSwitch` leaves the mark on for anything but `false`, and `sandcastle doctor`'s machine-wide settings check reports a value that is not a boolean. In `register.tsx` the two are drawn apart: the status line (`$.ui.status`, which Claude Code gives a warning triangle and its notice colour, neither of which a mod can change) holds only the needs-you text while a live run needs a person, and the mark is the `sandcastle.mark` state that the `AbovePrompt` band draws as one `Text` in the status view's sand (`SAND.name`) above the castle, absent while any run the band draws is alive - the session root's own or a followed one elsewhere - since a mark above a castle reads as a second, stale queue; its count is always the session root's project's. A person's choices are `/sandcastle-mark` (`markAction`, answered by a `command.run` with text and no model turn): `hide` and `show` set the hidden flag, `dismiss` records the ids of a count that is current (`choiceAfter`; a count too old to show was not seen, so it records none), `show` clears both, no argument is `markReport` (the state, the cached count and its age) and any other word is `MARK_USAGE`. The choices are one `Choice` in `$.store` under `mark:<root>`, beside `ready:<root>`: machine-local, kept across a restart, never in the repository, checked by `parseChoice`. `markText` gives no line when hidden, and no count while a dismissal holds - the current ready ids all within the dismissed ones (`dismissalEnded` is the other case: an id not in them, and an id leaving ends nothing); the idle look also clears the stored dismissal when it ends, so it is over for good, not only while the new id is ready. A hidden mark makes no queue read. A choice made while the mark is what the line shows redraws it at once (`idling`), not at the next look. `test/idle-mark.test.ts`, `test/idle-mark-choice.test.ts` and `test/idle-ready.test.ts` hold the module, `mod/tests/ready.test.ts` the count's hooks, `mod/tests/skill-turn-end.test.ts` the read at the end of the skill's turn, `mod/tests/mark.test.ts` the command's). It runs inside Claude Code, not under `tsx`, and imports nothing from `src/`. Its own tests are `mod/tests/`, run by `claude plugin test mod`

Verifying a change to it needs Claude Code 2.1.287 or newer on PATH: `pnpm test` then runs `claude plugin validate` and the mod's own tests (`test/mod.test.ts`), and skips them without it, as CI does; the kit's own sandboxes get it from `claudeCode: "latest"` in `.sandcastle/config.ts`, since the `stable` channel is older. That checks the hooks and the tree they return, never the paint: look at a changed drawing in a real session, `claude --plugin-dir mod` from a project with a run record. The mod's API is early access, and its types are the authority, not memory. That session writes them to `mod/.claude-plugin/types/` with a `mod/tsconfig.json` (both gitignored; they are absent until then, and `mod/types/index.d.ts` holds only the band's own types); from then on `pnpm test` type-checks the mod too, which the kit's own `tsc` does not cover. Grep the types for the member you need rather than reading them: they run to thousands of lines. `claude plugin test mod` reporting "hooks modules are turned off" is Claude Code's rollout switch, not the mod.
