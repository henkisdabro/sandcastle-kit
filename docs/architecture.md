# Architecture notes

What each of the kit's larger modules owns, in more detail than `AGENTS.md`'s Layout table. Read
the section for a file before changing it; update it in the same commit when a rule here changes.
The terms (run record, attempt, ending, requeued) are defined in `GLOSSARY.md`.

## `bin/sandcastle`

Shell entry; resolves symlinks, checks the temp directory can be written, runs `src/cli.ts` in one node process on Node's own type stripping, after `src/node-check.mjs` has refused a Node without it (never a wrapper that runs the CLI in a child: tsx's binary did, and SIGKILLed it on a slow answer to SIGTERM); `sandcastle herdr ...` runs `src/herdr-plugin.ts` alone, as Herdr's tab bar calls it every 10 seconds

## `src/cli.ts`

Commands: help, `--version`, setup, doctor, init, updated, changes, build, gates, land, preview, lean, lean-apply (internal hook), preflight, queue, requeue, blockers, run (`--detach`), wait, stop, pause, resume, report, status, clean, herdr; also the autonomy loop around `burndown()`. The help text and each command's `--help` come from `src/help.ts`

## `src/burndown.ts`

The orchestrator: base gates, then every attempt and landing through `createSchedule(plan).run(work)` (the attempt port: implement, review, gate with repair, in the pipeline `createPipeline(ctx)` makes; the land port: merge or squash, on the landing worker as each ticket goes green), then verify and report; it records what the scheduler tells, handing each ending to the ledger (`src/ledger.ts`), and posts the hold notes and the comments the ledger words after the schedule; the attempt reports its pipeline (`attempted`) with the agent's hand-back read as it ends (`handBack`) and the `.git` check at its end (`settleAfter`, the settle's check, made before its sandbox closes, once its container is stopped, with the worktree's records - `checkBeforeClose`, `src/guard.ts` - so a failure removes the container without Sandcastle's close), whose failure stops the run without replacing the pipeline's own ending, and writes only the pipeline's facts (commits, minutes, tokens); dependencies, the files the scheduler's hold compares (`ticketFiles`, `refreshFiles`: one ticket at a time per file git cannot merge) and the record of what it tells (`createHoldRecord`), re-runs of carried branches (land-only, narrow review; a branch reviewed but never green is land-only too, from `reviewedOnlyHead`, unless its head record's `red` says its gates ended red at that tip; a branch left with no commit ahead of the base is no carried work, so the pipeline's setup cuts it from the base's tip again before its sandbox opens - `cutFromBase`, through `host.write`, after `host.begin` so the `.git` check reads the new tip as the pipeline's own move, and a branch a worktree holds is moved only with a clean kept worktree under `.sandcastle/worktrees/` (a killed run's, fast-forwarded in place with `git merge --ff-only --no-overwrite-ignore`, branch and checkout together; the clean check leaves ignored files out, so the flag makes git refuse, not overwrite, one the base now tracks, its installed dependencies kept, once its records pass `assertWorktreeRecords`) - one with uncommitted or untracked files, or outside `.sandcastle/worktrees/` (a person's own), is left, as git refuses to move its branch; `test/stale-empty-branch.test.ts`, `test/stale-empty-branch-kept-worktree.test.ts`; a kit worktree Sandcastle's open would reuse - holding the branch, or at its path - has its records checked before the open too, at the setup and at a resume, `test/guard-worktree-records.test.ts`), timings. A red gate whose failing tests all lie in files the branch did not change (`failingTestFile`: pytest's `path::test`, vitest's and jest's `FAIL path` - a workspace project's label (`|web|`, or a bare word before a file) is skipped, and `failingTests` strips colour codes, as `runGates` does from a red gate's failure output (the gates log keeps them) - and node:test's spec summary, whose `test at <path>:<line>:<col>` line above each failing test gives `path::name`; a test whose file the output does not name, or names outside the repo, is the branch's own - so is node:test's red when its `✖ failing tests:` summary was cut off, or under Node 20 and 22's TAP default, whose absolute `location:` paths are not read) is checked against the base: `redOnBase` in `createPipeline` runs every gate once per base tip through `gateBase` (`baseGate`, a promise cached by the tip, so branches red together share it, and filed under the commit its sandbox gated - `GateRun.head` - when a landing moved the base in between), and a failure whose tests are all on the base's whole failing list (not the first five) gets no repair pass, is printed once as `base went red mid-run: <test>` and is kept once in the run record's `baseRed`, which the closing summary lists under Needs you (`test/base-red-mid-run.test.ts`, `test/base-red-check.test.ts`). An id that names only a file (`FAIL path`, a node:test file that failed to load) says nothing of which test failed, so with one the red is the base's only when the gate's `failureKey` is the same on the branch and the base

The pipeline takes everything outside itself through one `PipelineContext`, as a landing takes its `LandContext`: its sandbox (`open`, whose `run` is every agent pass and `exec` every git command in it), its gate runs (`gate`), the step timer (`timed`), and what the run keeps across a ticket's attempts (`requeuedAs`, `results`, `reds`, the heads record under the project root), the run's landings so far (`landed`: who a branch that no longer merges collides with), and the fix board it shares with the run's other pipelines (`fixes`, `src/schedule.ts`). `test/pipeline.test.ts` drives it over a temp repo with a worktree for the sandbox, scripted agents and scripted gate runs: a change to the pipeline is tested there, by what it does, not by matching the source of `src/burndown.ts`. A repair pass counts in the outcome's `repairs` only when the branch's tip moved over it; one that left the tip where it was is in `idleRepairs`, which a requeue carries as it does `repairs` (`firstAttemptIdleRepairs`), and the per-ticket line words (`repairWords`, `src/ledger.ts`) as `repaired=N` and `repair made no change` (`test/pipeline-repair-no-change.test.ts`). The verify records the image it ran on - the run's own, built before any ticket landed - and the Dockerfiles the run's merges changed since (`changedDockerfiles`, `src/gates.ts`: the kit's `docker/base.Dockerfile` and the config's `dockerfile`) in the run record's `verify`, so the closing summary's re-gated line can say the new image is untested (`test/report-regate-image.test.ts`). A red verify also compares the base tip's tree with the tree each landing left (`landingOfTree`, `src/landing.ts`, over `LandContext.landed`; a landing's tree is the one its gates passed; with the files tracker a difference only under its ticket directory, the tracker's close and follow-up commits after the landing, still matches - `test/verify-same-tree-files-tracker.test.ts`): on a match with a fast-forward landing (its ticket's own sandbox) the run record's `verify.gatedTree` names that ticket, and the summary's re-gated line and first next step say the red is the sandbox's, not the merge's, instead of `RED TOGETHER`; on a match with a landing merged in a landing sandbox (`clean` on its `landed` entry), a clean sandbox like the verify's, `verify.cleanTree` names it and the summary says a test is likely flaky or order-dependent (`test/verify-same-tree.test.ts`). The verify is **proof that the merged base is green in a clean gate-only sandbox**, not a clean re-gate on purpose: the green-base record (`.sandcastle/.run/base-gates.json`) holds the commit, the key (commit, image, plan and config), `by`, whose gates proved it (`#427` for a landing, `the base check`, `verify`) and `kind`, where they ran (`ProofKind`, `src/gates.ts`): `landing-sandbox` (a merge gated in its landing sandbox), `base` (the base check), `verify` (an earlier verify) or `ticket-sandbox` (a fast-forward of the tree the ticket's own gates passed on, in the sandbox its agent worked in). When `greenProofOfBase` finds the record at the base's current tip on the run's image and plan, **and its kind is one of the first three**, the verify does not run: the run record's `verify.skipped` carries the commit, `by` and `kind`, and the summary says `Merged main re-gated: green at <sha> already (gated with #427 in its landing sandbox) - not run again` (`verifySkippedLine`, `src/report.ts`). A `ticket-sandbox` proof never skips it, and it is due for one merged ticket as for several (`verifyPlan`, `src/gates.ts`: at least one ticket merged, or a merge regenerated files; a run that lands exactly one ticket as a fast-forward leaves a `ticket-sandbox` record, so its verify runs, while one merged in a landing sandbox leaves a gate-only record and skips it): that sandbox differs from a gate-only one (the agent's git identity in `~/.gitconfig`, for one), and a base red in a clean sandbox passed the ticket's own gates. A record from an older kit has no `kind` and is no proof either. The next turn's base check reads the record with `baseCacheHit`, whatever its kind. A missing record, or one at another commit (a landing's note is swallowed when it fails), runs the verify as before (`test/verify-skip-green-base.test.ts`). A landing's or verify's record keeps `hooks: true` (so the next base check opens no sandbox for the hook tests and the git-hook probe) only when the record before it had it, at a commit it names and the same key, and `git diff --name-only` between the two touches nothing under `core.hooksPath`, `.husky/` or `.git-hooks/`, no kept hook's command, no package manifest or lockfile and no protected path (`hookInputsChanged`, `src/gates.ts`; `test/hook-checks-kept-across-landings.test.ts`); anything else re-checks. The record also holds `hookRuns`, the commands of the kept hooks that ran cleanly (exit 0, or a block) in a passing hook test (`HookTestResult.clean`: a block test passes when any guard blocks, but vouches only for the guards that did not error), carried across such a landing with `hooks`; the lean hook check, which prints before the base gates, drops its unseen-import warning (`MODULES`, blind to a `sys.path.insert` made at run time) for those hooks only, when the record holds at the base's tip (`hooksThatRanClean`, `src/gates.ts`; `test/hook-check-vouched.test.ts`).

The pipeline is called with the scheduler's attempt arguments (`pipeline(issue, at)`), and awaits `at.juncture(phase, park)` before every step that would start an agent pass: resolve, the narrow and the full review, cross-review, the repair (before the fix board is consulted, so a ticket parked there claims no failure for the others to wait on) and the review after it, and implement - each *before* its `timed` step, so the wait is no pass's time. The juncture returns at once unless a person has paused the run (below, under `src/schedule.ts`); then `park.suspend` records the ticket as `paused` (note `before <phase> at <short sha>`), reads the sandbox's peak, stops its container and makes the run's `.git` check and the worktree's records check (`checkBeforeClose`; a failure removes the container, stops the run and parks nothing), unlocks its worktree and closes the sandbox - every commit stays on the branch, and a worktree Sandcastle keeps for uncommitted files is locked again against a prune - and the burndown's attempt gives the ticket's slot back (`leaseSlot`); `park.resume` leases a slot again (a landing that waits for one goes first, `slotTurn`) and opens a fresh sandbox on the same branch (`timed(..., "setup", ...)`, which reuses a kept worktree), so the pass begins from the ticket's own state in the pipeline: the phases done, the changelog and unmet lines, the reviewers' reports are all still there, and nothing is run twice. The attempt begins in the slot its worker leased (slot first, `at.slot`) and asks for a juncture, `"start"`, before the pipeline opens a sandbox, giving the slot back while paused; with no slot (the run was paused as the attempt began, so the scheduler gave the worker's back) it leases its own after the juncture, and asks for the juncture again before it goes on, so a pause that came during that wait starts nothing. Gate runs are no juncture, and neither is a landing: a pause lets both go on. One more place parks a ticket, inside a pass: with `USAGE_PAUSE` set, the pipeline's `pass` - which every agent pass goes through - catches a pass that failed with the plan's limit (`passHitLimit`: the last lines of *that pass's own* readable log, only what the pass wrote after the log's size when it began, since a re-run appends to the same log and a re-run that fails early would else read the limit message of the pass before it - the attempt's `hitLimit` reads every log of the ticket, and one an earlier run left saying so would send a pass that failed for another reason into a pause and a rerun, again and again; not the cross-review, a second opinion that never stopped a run) and asks the context's `limitPause(phase)` (`createUsagePause(...).limit`, below, after a forced `usageWatch.poll(true)` so the newest reading is the pass's own last, not one up to 15 seconds old), which pauses the run until the window resets or answers false - when no reading says when that is, or the pause cannot be written - and then the error stands as it always did. Paused, the pass calls the same juncture - sandbox closed, branch and any uncommitted files kept, slot given back, a fresh sandbox on the same branch after the resume - and runs the *same* pass again in it (the ticket's note says so); a pass whose juncture did not park (nothing paused the run) fails rather than looping. The time parked inside a pass is that step's `waitMs` (the step line's `ms` and the ticket's usual time leave it out, as for a gates-slot wait) and is added to `waited` once, by `timed`. No wait for a machine-wide sandbox slot is a ticket's: its worker leased the slot before it took the ticket (slot first), so the per-ticket summary line (`ticketTime`) is the ticket's own time and the first `setup` line carries no slot wait; the run's waits are `createSlotWaits`' (`test/slot-wait-timings.test.ts`). A sent-back ticket's resolve wait, which also comes before the pipeline, is handed in as `at.resolveWaitMs`, and the first `setup` step takes it as `timed`'s `queuedMs`: `withQueued` (`src/gates.ts`) adds it to that line's `waitMs`, outside `ms`, and not to `waited`, since `took` never held it.

**Sandbox CPUs** (`sandboxCpus` in `src/sandbox.ts`): one function decides a sandbox's `docker run --cpus` from its kind - a `ticket`'s (the VM's CPUs divided by the run's concurrency) or `gate`-only (divided by `maxGates`: the landing opener, the base, mid-run base and verify gates, `sandcastle gates` and `sandcastle land`; the landings are one at a time and set the run's end) - the VM's count from the start's one `docker info`, a numeric `cpus` in the config overriding both, cut to the VM's. `burndown()` resolves both once per turn and carries each on a copy of the project, as `sandboxConfig` reads it: `project` is the ticket's from there, and `gateProject` goes to `sandboxOpener`, `requireGreenBase` and `gateBase`, so `src/gates.ts` and `src/land.ts` take no argument for it. `gateOnly` in `src/cli.ts` does the same for `gates` and `land`. A new place that opens a gate-only sandbox takes the gate project, or its gates run on a ticket's share; `test/sandbox-cpus-commands.test.ts` runs both commands against a fake `docker` and reads the `--cpus` each container got.

**Gates leave the worktree as they found it** (`runGates`, `src/gates.ts`): `git status` before and after, and the paths the gates changed - a tracked file a build regenerated, a build left untracked - are put back, whatever was dirty before them is not touched. Sandcastle keeps a dirty worktree and its branch at close, so one rewritten file used to leak every worktree the kit gated in, and the branch delete after landing failed. The tracked files restored are the `GateRun`'s `rewrote`, which `burndown()` keeps in the run record's `gateRewrites` once each, and the closing summary names with the way to stop it (`.gitignore`, or `generated`). A gate-only sandbox (`gateBase`) resets hard before it closes, as `landInSandbox` does. `test/gate-rewrites-tracked-file.test.ts`.

**Kept worktrees of earlier runs** (`earlierKeptWorktrees`, `src/report.ts`; `test/report-kept-earlier.test.ts`): the run record's `keptWorktrees` lists only what this run kept, so the closing summary also reads `git worktree list` for every worktree under `.sandcastle/worktrees/` (`projectWorktrees`, `src/sandbox.ts`, the listing `cleanProject` removes by) that the record does not list - `Facts.earlierKept`. Whether one is merged is `clean`'s own rule for its branch (`branchFinished`: nothing on it that the base lacks, or a `sandcastle/*` scratch branch); its disk use is `du -sk`, said from 1 GB. Local state counts them; the Next step names `sandcastle clean` for the merged ones (and says it removes the unmerged ones with their uncommitted files too). A live run's partial summary leaves out the worktrees of its own tickets and its scratch branches, which are in flight, not kept. The worktrees an earlier turn of a drain run kept (`Facts.carried[].facts.keptWorktrees`, `test/report-drain-carry-kept.test.ts`) are named like the last turn's own, in Local state and in the look-then-clean step for a merged ticket, marked with their turn, and left out of that count.

An agent names a problem outside its ticket in a `<followup>title - evidence</followup>` line, never with a tracker write of its own: the pipeline's `pass`, which every agent pass goes through, reads them (own-line tags, as `<changelog>` is read) into the context's `followUps`, with the ticket and the phase. The context's `followUps` is the run's follow-up book (`createFollowUpBook`): each line goes into the run record's `followUps` as its pass ends, an unfiled entry (no `id`), so a run that stops before the filing - the schedule rejecting, or a safety stop - still has them for its closing summary and the next run; a title is listed once, and not at all when an earlier turn of the run filed it. After the run's notes are posted, the book's `file` files each entry still unfiled through `fileFollowUps` and the tracker's `create` on the host writer (a ticket file is a commit on the base, so `trackerMade` checks it), a title once per run; a dry run files none. A line naming the same place (`placeSeat`) as one already heard from the same source ticket is the same finding in other words. A place is a file of the base tree (`exists`, `onBase`: `git cat-file` on the base branch, so `api.example.com:443` is not one and a root-level `status.sh:40` is), or a bare file name (no `/`, not a root file) that is the base tree's only file of that name (`named`, `namedOnBase`: one `git ls-tree` of the base per run; two files of the name, or none, is no place; a caller that gives no `named` resolves no bare name). A finding has a place for every file it names, in its title or its evidence (`Seat.spots`, kept in `places` under each file), and two findings are one when any place of one matches a place of the other: a `path:line` in a title is used as it is (the same line, whatever the titles), while anything else - a place found only in the evidence, a file with no line, a bare name - counts only when the two titles also share at least two significant words (4+ letters, no stopword, every path the title names excluded; `sameFinding`). `test/followup-place-forms.test.ts`. A line that names no place of the base tree is the same finding as one of the same source ticket that names none either when the two titles share at least three significant words (`sameFinding`, a seat with an empty path). Such a line: it is not listed, and once the first is filed `fileFollowUps` posts its evidence on that issue with the tracker's `comment` (`places`, the issue of each place, is shared by a run's turns like `seen`); a comment that fails is tried again by the next `file`, and a first that failed to file leaves it held, never filed as an issue of its own. The two stops file them too (`stopLanding`, before the summary is printed), except after a safety stop - the shared `.git` changed - where nothing is written to the tracker: each entry stays in the record as `failed` with that reason, which the report lists under Needs you as one to file by hand (a crash of the schedule is a safety stop when the host git refused a write, and otherwise the writer's own `.git` check refuses a write the fingerprint forbids). The run record's `followUps` keeps what each became, and the report lists them under Needs you - the filed ones, a dry run's and the issues opened during the run under a `### To triage` sub-heading after the run's own items - leaving the kit's own filings out of the issues "opened during this run". A review that names a gap in prose and files neither a `<followup>` nor an `<unmet>` line is caught by `gapOf` (the same pass of `createPipeline` reads it beside `ungatedOf`, for the full review, the cross-review and the review after a repair): the sentences with a gap word (`left alone`, `remains`, `gap`, `not fixed`, ...) that are not negated (`nothing remains`, `remains unchanged`), outside fences, tags and inline code (a Markdown heading or a short bold label - at most six words, no sentence punctuation, no colon with words after it - is no sentence either; a bold sentence is read as prose, its bold markers dropped), become the pipeline result's `gap` (a sentence opening with `That`, `This`, `It`, `These`, `Those` or `Which` is quoted with the sentences before it in its paragraph, up to `UNGATED_MAX`; "remaining ..., which is correct", "found ... and fixed" (unless a gap is named after the fix) and "left alone, as the ticket asked" are negated too), the ticket record's `gap`, and for a merged ticket a line under Needs you.

## `src/landing.ts`

`landOne(ctx, outcome)`: landing one green branch (tracker check, moved head, held paths, then a merge as it is when the branch holds the base's tip, otherwise git's own merge of the base tip and the head on the host - a conflict outside the `generated` paths is returned at once, before any sandbox slot is asked for - and then a merge gated in a sandbox, close) and what it returns - how it landed and the facts the run record keeps (the files a conflict or hold names, a red tree's failing tests, the paths beyond the Touches line, a close that failed twice, its error) - writing no verdict of its own, only the `landing` stage; `landingWork(ctx)`: the scheduler's land and host ports over one `LandContext`; the lines of a requeued ticket; `createHostGit`: the mutex through which every host git write goes and which moves the run's expected base; also the landing merge, its abort and the conflict line. What it posts to the tracker as it lands (the close comment, a hold, an earlier merge closed) it asks the ledger's `describe` for

## `src/ledger.ts`

The ticket ledger: one place that turns each ending (`src/schedule.ts`) into everything a run says about its ticket.

- **`describe(ending, context)`** is pure and exhaustive over the `Ending` kinds (the type checker holds it): the ticket state the run ends on, the **outcome** (kind, `with`, text), the view's word and whether it counts as landed, and the tracker's text (a close, a hold, or the one comment on a ticket that did not land). The context is what the ending does not carry: the base, the gates' names, the agents' report, a dry run, a kept worktree, a hold note (the ticket gets that note, never a second comment), the run's stop line. The agent's hand-back through the tracker's hold label is on the pipeline's result (`handedBack`), so the ending arrives complete. `test/ledger.test.ts` holds every ending's four sayings side by side.
- **The writer** (`createLedger`) records what `describe` says as burndown's `tell` hands it each ending (`ledger.tell`): the ticket state the run ends on, the outcome and the view's word - it is the only writer of each, so neither `landOne`, the attempt nor the burndown after the schedule writes a verdict. Its `outcomes` port is `outcomesFile`, the one caller of `recordOutcomes`. `test/ledger-guard.test.ts` holds that: outside `src/ledger.ts` a run writes only progress - a phase, the landing stage, queued or blocked, a note, the pipeline's facts - spelt out in each `.ticket(...)` call, and nothing calls `recordOutcomes`. Each ending is recorded once, as it is told; a ticket the run's stop left unstarted waits for the run's last words (`close(endings, stopLine)`, after the schedule: the most severe cause, which a ticket told earlier could not know). Beside the endings, `ready` writes a green branch as it waits to land, with its outcome and what will hold it for a person at landing. Each ticket's entry is kept.
- **A requeue** is a told change the writer records: the ticket written as queued with the line its second attempt's setup carries (`requeuedAs`), before it is pushed back. A second collision's note names the tickets of both attempts (`describe`). `landOne` writes no verdict, so a requeued ticket whose second attempt never began has nothing to undo: it is recorded from the ending the scheduler makes of it (its first landing, or withdrawn - then said as not started, and its first pipeline's line dropped), its record no longer `requeued`; a conflict its pipeline found before landing is recorded the same way, from its `conflict` ending. `test/landing-requeue.test.ts` drives the scheduler with this writer over fake ports.
- **`accountLanding(entries)`**: what the closing notification and the verify read - the merged list and the counts - from the entries.
- **`partly-done`** is a landing ending: a branch an agent said leaves an acceptance criterion undone (its `<unmet>` line, read by `unmetOf` as `ungatedOf` reads `<ungated>`; the reviewers' word replaces the implementer's once a full review ran: the full review prompt shows the implementer's line as `{{IMPL_UNMET}}` - empty when there is none, and for a narrow review - and asks the reviewer to finish the criterion or restate it, so a line it does neither with is dropped from the ticket's leftovers; that prompt also shows the ticket's comments, as the implement prompt does, and the last paragraph of the implementer's final message as `{{IMPL_SAID}}` (`closingParagraphOf`, `implSaidView`), so a check the implementer says it did not make reaches the reviewer; the paragraph is kept in the head record's `implSaid`, as `unmet` is) merges, but the ticket is neither closed nor released to its dependants, and the ledger's comment names the criterion. Its merge subject says `part of` the ticket, not `closes` it (`mergeSubject`), so `mergedEarlier` does not close it on the next run, which picks up the remainder while the ticket stays queued (`Facts.partial`, read from the tracker by `gather`; `partialRerunnable` makes it re-runnable for the autonomy loop, and `drainStop` stops a drain that leaves the same ticket partly done twice). An `<unmet>` line that `needsDecision` reads as needing a person (the agent's explicit `<unmet who="person">` marker, which `unmetOf` keeps as a `needs a person: ` prefix on the note, else its words: a decision, a deploy, access it lacks, a file agents may not edit) is not re-runnable: the ledger comment and the report suggest the hold label instead.
- Also the words themselves: `closeComment`, `partlyDoneComment`, `notLandedComment`, `pipelineOutcome`, `refusedRecord`, `withdrawnRecord`.

## `src/resolution.ts`

`withObjectsOnly`, through which every host `git merge-tree` runs: a temp git directory with no config, no `info/` and no refs, borrowing the shared object store as an alternate (`GIT_ALTERNATE_OBJECT_DIRECTORIES`), removed in a `finally`. A sandbox can write the shared `.git` while its ticket runs, and a merge driver in `.git/config` mapped by `.git/info/attributes` would otherwise run on the host at the next merge-tree, before any fingerprint check; the objects git writes stay in the temp directory too. It never fetches (no remote, no promisor settings: the remote's address is read from the `.git/config` a sandbox can write, and a fetch would spend the operator's credentials), so in a partial clone a check that needs a missing object fails; `noteMissingObjects` recognises that, says so once and keeps a note for the run record's `mergeUnchecked` and the closing summary, and `sandcastle doctor` warns on a partial clone (`isPartialClone`; `test/partial-clone-merge-check.test.ts`). `mergeTree` and `mergeTreeSupported` (git's own merge through it, and its git 2.38 gate, which `landOne`'s conflict precheck and the pipeline's `conflictBefore` share; `plainMergeNote` in `src/land.ts` runs its merge through it too; `test/merge-driver.test.ts` plants a driver and holds all four); `strayChanges`: compares a conflict resolution with git's own automatic merge (`git merge-tree --write-tree`, git 2.38 or newer) and names the changed paths that merged cleanly and that the base side could have put another ticket's lines in - a path `theirs` changed since the merge base (`merge-base --all`, a criss-cross history has several), or one the merge changed in `ours` (a rename of the branch's that received the base's edits to the old name) - so the land-only path holds the ticket instead of reviewing a resolution that dropped another ticket's lines; a new file the resolution adds, or one only the branch touched, can carry none and goes to the narrow review (`test/resolution-base-side.test.ts`)

## `src/schedule.ts`

`createSchedule(plan)` is the run's one path for attempts and landings: `start` (the candidates in
start order) and `run(work)`, which resolves to each ticket's typed **ending** and the run's stop
state.

- **Ports.** `attempt` (with `last()`, true once nothing more will start), `land`, `host` and `tell`.
- **Requeue once.** A first conflict or red at landing gets a second attempt carrying what it
  collided with, unless the run starts nothing. The pipeline can requeue too: a branch that no
  longer merges onto the base, by git's own merge on the host after implement (before review) and
  again before the gates (`conflictBefore` in `createPipeline`; a conflict only in `generated` files
  does not count), ends its pipeline there and the attempt reports a `conflict` (`Attempted`),
  never a green - the gates vouched for no commit of it - and that conflict goes through the same
  rule as one at landing (`sendBack`); not sent back, it ends as a `conflict` (`Ending`), and sent
  back with no next attempt, it ends on that conflict as a landing does on its own
  (`test/pipeline-conflict-before-landing.test.ts`, `test/ledger-conflict-before-landing.test.ts`).
  The ticket is told before it is pushed back; a second collision is final. A red one is repaired from the landing gate's own output, with no gate
  run, when the requeue's merge joins the base tip and branch head that gate ran on
  (`repairFromRed`, `src/landing.ts`); on a moved base the gates run first. A conflicted ticket's
  second attempt does not begin at once: it waits until no green branch that shares a file with it
  is queued to land and no ticket still in its pipeline has touched the files it conflicted on,
  then merges the base and resolves once (each landing ahead of it would have conflicted the resolve
  again; the wait holds no sandbox slot and no pipeline worker - the worker that takes the ticket
  hands it to the wait and goes back to the queue, and the ticket is pushed again, first in line,
  once nothing is ahead of it - and is not in the run's demand, and ends at a stop; a pause
  parks it as at the start; the run says `resolve waits` once the list has held for `RESOLVE_SETTLE_MS`
  (the log line once, a later change only the record's note; a ticket still in its pipeline is worded
  "lands or leaves the run", a queued branch "has landed") and `resolve starts` for a wait it said,
  `test/schedule-resolve-wait.test.ts`, `test/schedule-resolve-worker.test.ts`, `test/schedule-resolve-settle.test.ts`). A second conflict is still final, unless it names a ticket
  that landed after the resolve began (the resolve's merge could not hold it): that one sends the
  ticket back again, with the same wait, and each such requeue needs a new landing, so it ends.
- **Release of dependants.** The tickets held for a blocker that starts in this run: when one lands
  and closes, the blockers of the ones that waited for it are read again through the plan's
  `blockers.open` port, and each with none open starts through the file hold. Any other ending, a
  run that starts nothing or a dry run releases none, and each held ticket is told what it waits
  for now.
- **Start order.** The pipeline queue ranks what waits for a sandbox slot: a requeued ticket first,
  then a released dependant, then every ticket not yet started, each group in the order it arrived.
  Both have waited already, and every landing before they start moves the base under them; behind the
  unstarted tickets they became the run's last landings while slots sat idle. A ticket freed from a
  file it shared keeps its place with the unstarted. The run prints `#N released: its last blocker has
  landed; it starts at the next free slot` when a dependant is released (the start of one freed from a
  file reads `starts:`), and the status view's queue position follows the same order (the hold
  record gives a requeued or released ticket an `order` below every unstarted one's).
  `test/schedule-start-order.test.ts`.
- **Slot first.** The rank decides when a slot is granted, not only which ticket a free worker takes:
  a worker leases its machine-wide sandbox slot through `Work.slot` and only then takes the head of the
  queue (`Queue.ready`, `Queue.takeNow`), and hands the slot to the attempt (`at.slot`), which gives it
  back and leases another across a pause and releases it as it ends. A worker that took its ticket
  first and then waited for a slot left every worker parked on a later ticket, so a released or requeued
  ticket waited out each of their pipelines. A worker asks the pool only while more tickets are queued
  than workers already asking, none while the run is paused (no ticket starts; a wait in progress ends,
  as `wanted()` turns false) and none once the run starts nothing (each queued ticket ends as not begun,
  with no slot). A worker whose ticket goes off to wait for its resolve keeps the slot and takes the next
  head - unless a landing of the run waits for a sandbox slot (`Work.landingWaits`, burndown's
  `slotWanted`): the kept slot never passed through `slotTurn`, so it goes back to the pool and the worker
  asks again, and the landing goes first (else it waited out the next ticket's whole pipeline, and the
  resolve waited on it; `test/schedule-kept-slot-landing.test.ts`). A worker still asking then ends its wait once nothing is queued (`wanted()` again), or a run with no
  demand left beside a hungry run would wait for ever (`test/schedule-slot-stale-ask.test.ts`). A ticket's wait for a slot is therefore zero; the wait is the run's (`createSlotWaits` in
  `src/burndown.ts`: the run record's `waitsForShare` and `waitsFor`, which the status view's next-to-start rows say,
  and the heartbeat's `waiting for a sandbox slot`). The demand is counted as before, from the push.
  `test/schedule-slot-first.test.ts`.
- **Endings.** The queues stay open until every ticket has its ending; on each ending its files are
  freed and its dependants released before the open count drops.
- **The file hold** (the scheduler's own too). A ticket sharing a file git cannot merge with one in
  flight is parked until that one lands or leaves the run. It is decided for the start as the
  schedule is made (`start`: the candidates in start order, each with its wait, before the run
  record exists) and told as the run goes (`started`, `waits`, `next run`). Mergeable shares are
  only named: one line per shared file listing its tickets (`fileShareSummary`; README.md and CHANGELOG.md are one count), the pair list in `.sandcastle/logs/file-shares.log`. A ticket in flight has its branch's files read again before each comparison; a run
  that starts nothing tells each parked ticket it waits for the next run; a dry run (no `files`)
  holds nothing.
- **The fix board** (`createFixBoard`, `FixBoard`). Which ticket is repairing which failure
  (`failureKey`): a pipeline `claim`s it as its repair pass starts and asks `fixing` before its own,
  and a ticket red on a failure another is repairing prints `#N: waiting for #M's fix to <test>`,
  `wait`s for that ticket's ending (`told`, fed every change by burndown's `tell`), then merges the
  base into its branch in its sandbox and gates again. A ticket red on a failure whose fix has
  already landed (its gate finished just after that landing) merges the base and gates again the
  same way, without a wait or its line - unless its branch holds the fixer's landing already (the
  board keeps the commit that put the fixer on the base, read from the landing record as the ticket
  ends, and burndown checks it with `git merge-base --is-ancestor`): the ticket started after the fix, the merge
  would bring it nothing, and the red is its own, so it repairs at once. A landing with no commit
  on record merges as before. A ticket that did not land (red, gave up, crashed, held,
  stopped) or was sent back, at landing or by its pipeline (`requeued`: its second attempt may sit behind the very
  pipelines that wait for it) frees its waiters, which repair as before. A ticket sent back keeps
  the failures it had claimed until it ends: its second attempt is often a land-only one with no
  repair pass, so when it lands, its landing is the fix to them (unless another ticket claimed one
  since and is still repairing it), and a later red on one merges the base instead of repairing;
  one that ends without landing leaves nothing. A wait also ends when the run is paused (`wait`'s
  `paused`, the attempt's `paused()`): the fixer may be parked at its own juncture and unable to land, and the
  waiter would hold its sandbox and slot through the whole pause. The waiter goes round the repair loop
  again: its `repair` juncture parks it (sandbox closed, slot given back, demand 0), and after the resume
  it asks the board afresh - the fixer may have landed, and then the fix is merged as above
  (`test/fix-wait-pause.test.ts`). A merge that conflicts and a re-gate that is
  still red also send a waiter to repair (it waits once per failure). A wait that would close a
  cycle is refused, a forced red (`SANDCASTLE_TEST_RED_GATE`) never waits, and the waiting ticket
  keeps its sandbox slot - so while a landing of the run waits for a slot (`slotWanted`), every
  waiter stops waiting and repairs, as the slot it holds may be the one that landing needs. A
  ticket that repaired before it waited keeps those commits under the review after repair.
  `test/fix-wait.test.ts`.
- **The pause** (`Work.pause`, a `PauseSource`: `read()` answers the pause in force, `{ since }` in seconds, or none). The scheduler reads it at each juncture and every `pollMs` (1 s; the timer is not unref'd - with every ticket parked nothing else may keep the process alive - and ends with the schedule), and tells `{ kind: "paused", since, finishing }` as it begins (before the first demand, when it was asked for before the schedule began) and again whenever `finishing` changes, `{ kind: "resumed" }` as it ends. `finishing` are the tickets still doing something that is not a juncture: inside an attempt and not parked, or a green branch queued for landing or landing. A ticket that has not begun stays in the queue: no worker asks the pool for a slot while the run is paused, and a worker's wait for one ends (slot first, above). One a worker took as the pause began waits before its attempt does, its worker's slot given back first (`attempt` holds it at `"start"`, unless the run has a stop cause: then it is not begun, as before); a ticket inside an attempt reaches `at.juncture(phase, park)` (the attempt port's argument) before an agent pass, which returns at once while the run is not paused, and otherwise runs `park.suspend()`, waits for the resume, and runs `park.resume()`. Landing goes on: the landing worker, a requeue's second attempt (which waits at its start like any other) and the release of dependants are not paused, and the stop state is read as before. A stop cause that arrives while the run is paused wakes every parked ticket (`noticeStop`, at the poll or at any ending), since a pause that only a resume ends could outlast a run that can do nothing more - under a usage pause, until the window resets: a ticket parked at its start ends as not begun - and so does one woken at an attempt's `"start"` juncture before any other, with a requeued one's earlier landing as its ending (`test/schedule-attempt-count.test.ts`) - and one parked at a later juncture finds `stop.startsNothing` after `waitParked` and throws `StoppedWhileParked` instead of calling `park.resume()` - its sandbox stays closed, and `burndown()`'s pipeline skips closing it again (`closedWhileParked`) and lets the error through to the attempt, which throws it on with the `.git` check after the pipeline (`attempted`): the scheduler adds a failed one as a cause, as after any other attempt. The schedule ends it as `parked` (`Ending`; the ledger says nothing of it, so its record stays `paused` with the juncture's note) and the closing summary lists it on the `Runnable now` line, whatever stopped the run: one that is not live is not paused, so a ticket still `paused` was parked when it ended. A pause and a resume that end together is a resume, as before. The same notice tells `{ kind: "pause stopped" }` once, when a stop cause arrives while the run is paused, and `tellPaused` tells nothing after it (the finishing list changing is not a pause to record again; a resume read later tells no `resumed` either): `createPauseHandling` clears the run record's `paused` then, while the tickets in flight finish, so the Herdr sidebar and tab bar (`runCounts`) stop saying paused (`test/stop-clears-pause.test.ts`). `test/stop-while-paused.test.ts`, `test/stop-while-parked-check.test.ts`, `test/report-parked-usage-stop.test.ts`. The run's **demand** counts, while paused, only the tickets inside an attempt that are not parked (`active`), plus the one for a landing: nothing in flight is 0, which `burndown()` hands to `setDemand`, so the machine pool gives the run's share to the others (`test/pause-pool.test.ts`); a resume drops the parked tickets from the count before any of them asks for a slot again (it is told first, as every demand is). A resume wakes every parked ticket; one that is paused again before it continues parks again. A source may say why the run is paused: `read()` answers `{ since, usage? }`, `usage` (`UsagePaused`, `mod/hooks/run-record.ts`) set while the pause is the run's own, for its plan's usage (`USAGE_PAUSE`, below, `src/usage.ts`). The scheduler passes it to `tell` on the `paused` change and tells the pause again when it changes while in force - a later window to wait for, a person taking the pause over (`usage` gone, `since` kept) - since the key it compares is the finishing list and the cause together. A pause that ends by itself is the source's business, not the scheduler's: it answers undefined once its time has come, and the next read is the resume. `test/usage-pause.test.ts`. `test/pause-resume.test.ts` drives it with fake attempt and land ports and a pause source, and the pipeline under it over a temp repo.
- `createStopState`: the stop state, whose `add` only the scheduler holds.
  The scheduler tells `{ kind: "stopped landing", cause }` once, the first time `landsNothing` holds - from an ending, a stage change or the poll, since the host's refused write is read live and no one adds it - so burndown prints `STOPPED landing: <what moved> (<detail>) - the run finishes what is in flight and lands nothing more.` and records `stopped` (which the status view's run cell reads) as it happens, not in the closing summary. The words are `ledger.ts`'s `causeWords` and `stoppedLine`: a `.git` stop is a `GuardStop` (`guard.ts`: `what` in a few words, `detail` for a person), so a ticket the stop kept from starting reads `not started: main moved while sandboxes ran`. A `blocked` change carries `ended`, the candidates that ended without landing, which `blockedNote` words by each one's state (`ledger.endedAs`: `stopped`, `gate red`, `not started`): a blocker of the run is never "not in this run". `test/stop-announced.test.ts`.
- `createLanding`: the one worker that lands each green ticket, a carried branch first.
- `createQueue<T>(rank?)`: the work queue of the pipeline fan-out and of the landing worker (`push`,
  `close`, `run(workers, fn)`). Workers wait while it is open and empty, so an item can be pushed
  mid-run; a higher `rank` goes first, equals in arrival order (the pipelines' rank is the start
  order above; the landing worker's puts a carried branch first).

## `src/pool.ts`

The machine pool: sandbox and gate slots shared by every run on the machine, and the lock-file helper the run lock shares (`takeLock`: pid and token, guarded takeover; `withLock`, and `withLockSync` for a caller that cannot wait on a promise: it falls back to running unlocked after `timeoutMs`). A **slot** is a lock file `<pool>-<n>.lock` whose line reads `<pid> <token> run=<id> <label>`: the pid stays first because `status.sh` reads it, and `run=` names the holding run (`RUN_ID`, one per process) so `slotsByRun` can count slots per live run. A lock from a kit that named no run reads as a run of its own pid.

`withSlot(pool, label, fn)` is `leaseSlot(pool, label)` with the release tied to `fn`'s end; `leaseSlot` hands the slot over (`release()`, once) for a ticket that closes its sandbox mid-way and takes a slot again later: a paused run's tickets (`src/burndown.ts` `attempt`).

A freed slot goes to the **longest wait, across runs**. `withSlot` writes a wait entry (`waits/<pool>-<since>-<run>-<n>.wait`, `<pid> <run> <since> <label>`, renamed into place whole) before its first try, and takes a free slot only when no other live run has an older entry for that pool (ties go to the lower run id), then removes the entry. Without it the run that has just freed a slot asks again at once and almost always wins, and a second project's run waits until the first drains. The rule is per pool, so a run holding a sandbox slot and waiting for a gates slot cannot deadlock on it. Within a run, a wait that asked for no priority yields to the run's other such waits that began earlier (`earlierAhead`: the earlier start, then the order they asked in), for either pool. A pipeline's wait names no ticket - its worker takes the head of the start queue once served (slot first, `src/schedule.ts`) - so this orders the run's workers and its tickets resuming after a pause, never one ticket's rank against another's. A run's landing asks for its sandbox slot with priority (below), so it goes before the tickets already waiting, and `slotTurn` (`src/landing.ts`) keeps the run's next pipeline from asking while it waits. The gates pool has one order inside a run, **landing first**: the one landing worker sets the run's end, and its gates waited for a gates slot behind the same run's ticket gates, minutes added to the serial path of each landing. `withSlot`'s last argument, `priority` (`leaseSlot`'s last too), marks a wait the run's end waits on: `landOne`'s wait for a landing sandbox passes it, and `runGates` passes it (its last argument) for a landing's gates (`LandContext.gate` in `src/burndown.ts`, and `sandcastle land`'s), the base gates at a run's start and the verify gates; a ticket's gate pass and the mid-run base check do not (`gateBase` runs that one in a ticket's own slot, `ownSlot` false). When a slot frees, the run is picked as before, by its longest wait; then a priority wait of that run takes it before the run's other waits for the pool. A priority wait counts from the oldest wait its run has for the pool (`countedFrom`), so it is not left behind another run that began waiting after its own run did, and any other wait of the run yields while one of the run's priority waits is waiting (`priorityAhead`). A run with no priority wait is served as it always was, and a run that has waited less than another is still behind it, priority or not. The priority is kept in this process (`OwnWait`, the entries in `waiting`), not in the entry file, which is unchanged: every wait of a run is this process's, and another run needs only a wait's start. A wait that yields to its run's priority wait can leave the slot idle for up to one poll, as a younger wait that yields to an older one does. A wait entry or slot whose process is gone (`holderRunning`, the run lock's rule) is ignored, a wait entry's removed when seen, a slot taken over by the next `takeLock`. A younger waiter does not take a free slot while an older one polls (every 5 s), so a freed slot can idle up to one poll. A run started by an older kit writes no entries and is not waited for.

An **extra slot** (`withExtraSlot`) is a sandbox started inside a slot its run already holds: the mid-run base check (`gateBase(..., ownSlot=false)`), which would deadlock a pool of one if it waited for a slot of its own. It is a lock outside the numbered ones, `<pool>-extra-<run>-<n>.lock` with a slot's content, written at once and never waited for, released when its function ends and at exit like a held slot; one left by a killed holder counts for nothing and is removed by the next extra slot taken. `usage()`, `liveSlots` and `status.sh`'s `<pool>-*.lock` glob count it, so other runs see every live sandbox; `tryAcquire` takes only numbered slots, so it blocks none. Accepted while it lives: `usage()` can read 7/6 (the status view's gauge draws no free cell then), and `members()` counts it in its run's `held`, so that run's other tickets may wait for their share - the share arithmetic is left as it is, since hiding the slot there would hide it from the other runs too.

**A wait that holds a slot.** Code that waits while holding a pool slot must not wait on anything that needs another slot - a ticket keeping its sandbox slot while it waits for a fix, a landing or another ticket's attempt that needs a sandbox slot of its own. Once every slot is held by such a waiter, nothing frees one and the run deadlocks; a test with one or two slots shows it. Release the slot before such a wait, or wait before taking it. Waiting for a gates slot while holding a sandbox slot is the one sanctioned case, as no gates slot holder waits for a sandbox slot.

The base image's build is one more lock of the same kind, `withLock` on `<cache>/locks/base-image.lock`: `ensureImage` holds it across the whole base step - build, prune of unused `sandcastle-base` tags, `docker tag ... :latest` - for any base tag, not per tag. Projects with different Claude Code versions build different tags, and one's prune would otherwise remove the other's fresh image before its `docker tag`; two builds of one tag race the same way. A second build waits, polling every second while the owner lives, then finds the image built and reuses it. Prune removes only a tag with no use for `IMAGE_KEEP_DAYS` (14) and no live kit process in its stamp: docker keeps no last-used time, so `ensureImage` writes a JSON stamp (`{at, pids}`) per tag under `<cache>/image-use/`, and a tag with no stamp starts its days at the first prune that sees it; checkouts on different commits hash different Dockerfiles, and "every tag but its own" made each delete the others' images. `build` reads docker's plain BuildKit progress (`watchBuild`): output is held until a non-`FROM` step does real work, and a build that only re-tagged cached steps prints `Image <tag> re-tagged from cache`; output of another shape, or a failure, is shown whole. A `docker tag` or `image ls` failure is an `OperatorError` naming the call and docker's message. The project layer's build and its prune are inside the lock too: its `FROM` names the base tag, which another project's base build would otherwise prune before the layer's `docker build` resolved it.

**Shares** (`docs/adr/0001`): live runs split the sandbox pool equally, up to each run's demand. A run registers with `joinPool` (`burndown()`, once per process: an autonomy run's next turn updates it) in `runs/<run>.run`, a JSON line written whole and renamed in: `pid`, `run`, `project`, `demand`, `concurrency`, `since` and `shares: true`, the mark of a kit that knows them. A registration whose process is gone (`holderRunning`) is ignored and removed when seen, and the file goes with its process. `members()` lists every live run that is registered or holds a sandbox slot, with its share: `splitShares` divides the limit equally among the runs whose demand is above 0, a run that needs less than an equal part releasing the rest to the others, again equally, in whole slots (the earlier registration gets the odd one, so every run works out the same split from the same files). A run with slots and no registration is from an older kit (or a command that is no run): it is counted as wanting its concurrency, read from the run record that the live-runs directory and the record's `pid` lead to, or the slots it holds if that cannot be read, and takes no share on trust. The share is taken by `withSlot("sandboxes")` of a registered process only: a run at or above its share (`held` counts) takes no slot while another run below its share wants one - a registered run below its share does, whether or not it has a wait entry at that instant (its demand is what it asks for next, so a run between two of its tickets is not mistaken for one that wants nothing), and any other run does with a wait entry - and with no one wanting one a free slot is taken as before. The wait order skips waiters that are at or above their share, which cannot take a slot, so an older wait of such a run never idles a slot. A slot held is never taken back. The check and the take are one synchronous step, so a run's own waiters cannot both pass it. `withSlot`'s `onWait` is told why a wait waits (`slots` or `share`, again when it changes), and `myShare` reads this run's demand, share and held slots. The gates pool has no shares. `inject` (`src/pool.ts`) replaces the pool's process check and clock, so `test/pool-sim.ts` can drive one run in the test's own process against other runs written as files (registrations, slot locks, wait entries) with a short poll: `test/pool-shares.test.ts` and `test/pool-cap.test.ts` run in about 2 s, where child processes polling in real time took 10-66 s a test under load. A registration going with its process, and the cap in it, is the one thing they still start a process for.

**Measured peaks** (`src/peaks.ts`, read by `src/size.ts`): `sandcastle size` sizes `maxSandboxes` and `maxGates` from what sandboxes used, not an assumed figure. `samplePeak` runs `cat /sys/fs/cgroup/memory.peak` through the sandbox's own `exec` (cgroup v2's high-water mark in bytes; no host-side `docker stats`, no container naming) after each `runGates` pass, which puts the largest reading so far on the `GateRun` as `peakMib` (a green `requireGreenBase` returns it too) - `timed()` in `src/burndown.ts` copies it to that step's `timings.jsonl` line, which `typicalTimes` and `estimate` never read - and `recordPeak` reads the peak once more just before the sandbox closes (a pipeline's `finally`, `gateBase` for the base and verify gates, and `landInSandbox` in `src/land.ts` for a landing's, filed under the run's `runId` from `LandContext`, or the time of a `sandcastle land`) and appends one `{ts, project, run, peakMib, sampled, anonMib?, agentMib?, agentAnonMib?}` line to `peaks.jsonl` in `KIT_CACHE`, beside `runs/` because that directory's files go once a run has ended (or, for a run whose own Herdr tab still awaits its report, once that report is typed). The largest reading of a sandbox, and each figure below, is kept in a `WeakMap` keyed by the sandbox. `project` is `projectId(root)`, a 12-character hash of the resolved root, and `run` the run's start time: no path or name is written (`test/peaks.test.ts` holds it), and a run is the lines that share `run`. Everything is best effort: a missing file, a failed or 10-second-late read or an unwritable cache records nothing and never fails a pass. `measuredPeak(peaks, now)` is the rule, pure: each project's figures over its last 5 runs (`RECENT_RUNS`), each the 90th percentile (`PERCENTILE`, nearest rank) of the samples (every line is one; `figureOf`), or the highest below 5 samples (`MIN_PERCENTILE_SAMPLES`) - so one outlier pass does not price every later pool - with `figures` carrying each one's sample count and highest, which `size` prints beside it, from the project with the highest peak of those whose newest run is within 30 days (`FRESH_DAYS`); it leaves out the two anon figures of a line without `sampled` (`SAMPLED`, 2: the readings below are taken only while a phase runs - an older line may hold the sandbox at rest, about 1 MiB, with nothing on it to say so, and its `peakMib` still counts), and any figure under `MIN_MEASURED_MIB` (256 MiB, the same sandbox at rest: it is not measured, so a gate with no anon figure is priced from `peakMib`, and a project whose `peakMib` is under it is not measured at all). `recommend(memory, cpus, peaks, now)` prices them, each plus 10% (`MARGIN`): a gate runs inside a sandbox, so `g` sandboxes are priced at the gate figure (`anonMib` when any run recorded it, else `peakMib`) and the rest at the agent baseline (`agentAnonMib` when the gate figure is anon and a run recorded it, else `agentMib`, else the gate figure). With `usable` the VM's memory less `HEADROOM_GIB`, `g = max(1, min(floor(cpus / CPUS_PER_GATE), floor(usable / gate)))`, sandboxes are `g + floor((usable - g x gate) / baseline)` clamped to 1 .. min(`MAX_SANDBOXES`, cpus), and gates `min(g, sandboxes)`; a VM whose `usable` is under one gate figure fits no gate sandbox, so its `byMemory` is 0 (never negative) and the output says it cannot fit one gate sandbox, while the pool keeps its least of 1 and 1; with nothing measured both figures are `PER_SANDBOX_GIB`, which the output says. Shares divide whatever limit is set. `memory.peak` includes page cache, so `memory.stat`'s `anon` (`readAnonMib`) is read too; it has no high-water mark, so only a reading taken *during* a phase describes it (after the gate loop the test workers have exited, so `samplePeak` reads only the peak, and at close the sandbox is at rest, so `recordPeak` reads no `anon`: a read after the pass counts towards neither figure, and was the whole of `anonMib` on a pass shorter than the interval). `sampling(sandbox, phase, fn)` reads it once as `fn` starts and every 10 s through the sandbox's own `exec` while `fn` runs, on an unref'd interval cleared in a `finally` (a periodic reading that answers after `fn` has ended is dropped, and the reads' own time limits are unref'd too, so nothing keeps the process alive; the first read, issued with the pass, is waited for when the pass ends before it answers, so a pass shorter than the interval still has a reading taken during it): `runGates` wraps its gate loop in it, and that is `anonMib`, the highest `anon` while a gate pass of this sandbox ran; a pipeline's `pass` wraps every agent pass (implement, review, cross-review, repair, resolve), the highest of which is `agentAnonMib`. `memory.peak` cannot be reset inside a sandbox (`/sys/fs/cgroup` is read-only there), so the agent baseline is read before the first gate: `agentBaseline` in the pipeline, between the review block and the gates step, once, and only when an agent pass ran there (a land-only re-run gives one only when a narrow review ran in its sandbox, after a resolve or for a carried merge), sets `agentMib`. Base, verify and landing sandboxes never set the agent fields, so a line without `agentMib` (every older line too) counts as a gate peak only. `poolWarnings` (doctor's `warn`, and `warning:` on a run's start line, both through `poolWarningsNow`) prices the effective limits the same way (`min(maxGates, maxSandboxes)` gates, the rest at the baseline) and warns when they need more than `usable`, only when the gate figure came from `anonMib` and the agent baseline is not `agentMib` (a baseline with no `agentAnonMib` stays priced from `memory.peak`, which `size` says includes page cache and may sit above the gate figure, as agents run the project's tests themselves): `memory.peak` counts page cache, and a pool it priced past the VM ran clean, so from it or the assumed figures doctor keeps its info pointer (`sizePointer`) and the start prints nothing.

**The cap** (`sandcastle cap`, `parseCapArgs`, `setCap` and `standing` in `src/pool.ts`; the command in `src/cli.ts`, which handles it before the repository check so `--project <name>` works from any directory): a person's limit on one live run's share, the optional `cap` field of that run's registration, so it ends with the run (a new run has a new registration, and an autonomy run's next turn is the same run and keeps it). `cap N` writes it, `cap off` removes it, a bare `cap` reads `standing()`. The run is found by the `project` its registration records, so the name is `loadProject`'s `name`; no live run, or two of one name, is a refusal, and so is a number above the registration's `concurrency` (the most a run ever wants) or anything that is not a whole number of 1 or more. The cap is written whole and renamed in, like the registration, and the run reads it as `members()` reads every registration, before each slot request. `splitShares` takes each run's demand as the smaller of its demand and its cap, so a cap only lowers a share and what it frees goes to the others up to their demand. `overShare` adds one rule: a run that holds its cap takes no slot even when no other run wants one (held, not share: with a demand below the cap the share is below it too, and a run with no rival takes slots past its share). Nothing is taken back: a run above its cap keeps its slots. The cap is a person's and written from another process, so the run's own copy of its registration never holds one: `writeRegistration` (a new demand) reads the cap from the file and keeps it. A cap set in the instant the run rewrites its registration can be lost - the person sees the cap missing in the next read-out and sets it again. The run record carries `cap` beside `demand` and `share` (`burndown()` rewrites all three when any changes, a lifted cap leaving the record); the status view's machine cell appends `· cap N`, and the Herdr tab bar line shows each run's `share` from its record.

The start plan also names, under the ticket list, each ticket whose `Touches:` line names a protected path (`protectedPlanLines` in `src/guard.ts`, over `protectedTouches`: `#N will be held for a person to merge (paths)`): it still runs, only its merge is a person's; and the live line of a ticket held at landing carries the hold's reason (`#N: needs a human: human merge: <paths>.`, from the ledger's record note; `test/protected-plan.test.ts`). The start line (`burndown()`, before the estimate): `otherRuns()` lists the live runs other than this one that hold or want a sandbox slot, `splitAtStart(demand, others)` works out the share this run would get beside them and how many slots are free this moment, and `startLines(split, neighbours)` words it - each registered run's project, slots and demand, this run's share, and when no slot is free the wait for the first (`firstSlotWait` in `src/run.ts`: the other project's `typicalTimes().issue` less its working tickets' ages, a minute at least, found through `recordOfRun(pid)`, the live-runs directory and the run record's `attemptStarted`, the current attempt's start (else `started`, the first); left out with no history). A run with slots and no registration gets a line of its own that says it predates shares; the run still starts. No other run: no line. The estimate's divisor is `estimateSlots(workers, split, landing)`: the workers within the run's share less the slot `keptForLanding` holds back (from a share of 2; `landing` is `!DRY_RUN`, as a dry run keeps nothing) when another run is live, else within the machine limit, and `startLines(split, neighbours, landing)` says the tickets' figure and the kept slot at a share of 2 or more, so the run record's `concurrency` and `load.concurrency` are the tickets' slots (`test/start-split.test.ts`, `test/start-kept-slot.test.ts`). `estimate` prices the run's tickets as their summed figures over the slots, floored at the slowest single ticket's figure (at the median and at the high end alike), not as `ceil(tickets / slots)` whole rounds of the average ticket: a sixth ticket on five slots starts when the first frees, and tickets on one model get identical figures from history, so list scheduling would not tell them apart (`test/estimate-slots.test.ts`). The chain, gates and landing bounds sit beside it and the largest wins; the tickets' figure ends with one more landing (the last ticket's), and a chain's is each link's pipeline and its landing, as a dependant starts only once its blocker has landed. The median (and 80th percentile) `base gates` and `verify` lines of the window's runs are added to the winner. `from N ticket(s)` is the history tickets that priced some ticket of the run, not the window's count (`test/estimate-whole-run.test.ts`, which also holds that a ticket's wait for another's fix goes into the pipeline context's `waited`, beside the gates-slot waits, and so out of the run record's `typical`). `estimate` also takes `limit("gates")` as `detail.gateSlots`: each history ticket's summed `gates` and `landing gates` line time (the wait is `waitMs`, outside `ms`) over those slots is a third bound beside the sandbox figure and the chain, and the largest sets the time (`test/estimate-gates.test.ts`). A landing gate writes a line of its own phase (`LANDING_GATES`, `timedLandingGate` in `src/gates.ts`, wrapped round the landing port in `burndown()`), which `typicalTimes` and `estimate` keep out of a ticket's own pipeline time. So does every landing that came to its merge (`LANDING`, `writeLandingLine`, told by `landingWork` through `LandContext.timed`; a landing decided without a merge - taken back, withdrawn, held, a moved branch, a dry run - writes none): its `waitMs` is `landOne`'s wait for a landing sandbox slot (`at.slotWaited`; 0 for a fast-forward and for a conflict found on the host first), its `ms` the rest, and its `result` the kind of ending. It holds the landing gates' time, so `typicalTimes` and `estimate` skip it too, or the landing gates count twice. A requeued ticket's resolve wait (`resolveTurn`, without the time a pause parked it) reaches its attempt as `at.resolveWaitMs` and is added to the `waitMs` of that attempt's first `setup` line (`withQueued`); a ticket has no slot wait to add it to (slot first). The landings in a row (the history tickets' landing gates, none for one that landed without a gate, summed over the run's tickets: one worker, whatever the slots) are a fourth bound, a floor on the end, and the estimate says when they set it. The gate and landing-gate times are priced by load: each run record carries `load` (`{ concurrency, tickets }`: the sandboxes it ran at once, after the machine cap and its share, and its ticket count; `burndown()` writes it, and it reaches `history.jsonl`), `estimate` joins the window's runs to it by `startedAt`, and when at least two of them ran within 1 of this run's slots, only their tickets price `gateMs` and `landMs`, and each history ticket's own gate passes inside its pipeline time are swapped for that `gateMs` (the four bounds combine as before). Otherwise - too few such runs, or older lines with no `load`, which count as unknown - all the window's runs price them and the line ends `No history at N at a time ..., so it may be low.` (`test/estimate-load.test.ts`). `typicalTimes` carries the same figure as `typical["landing gates"]` (the median ticket's landing gates, in seconds), from which `status.sh` takes the later of the pipelines' end and now plus the tickets not yet landed times that figure for `ends ~HH:MM` (`test/landing-gate-timing.test.ts`).

The demand comes from the scheduler (`src/schedule.ts`): the tickets from their push to the pipelines to the end of their attempt, plus one while a green branch waits to land or is landing, never more than `work.concurrency`, told as `{ kind: "demand" }` whenever it changes; `burndown()` hands it to `setDemand`. A ticket held for a blocker or a file adds nothing until it starts. The base gates (before the scheduler) and the verify run ask for one slot. Workers still start up to the smaller of concurrency and the machine limit: the share decides how many hold a slot. With landing on, `pipelineWorkers` leaves one slot of the machine limit out of the worker count, and beside another run (one that holds or wants a sandbox slot) the pool keeps one of the run's share: a ticket pipeline's lease (`leaseSlot`'s `keep`, which `burndown()` sets unless it is a dry run) waits, with the reason `share`, while the run's share is 2 or more and its ticket leases hold share - 1 (`keptForLanding`), re-read at each look as the share moves; a landing's lease (priority) takes the kept slot. While a ticket's wait is held back so, its wait entry is out of the waits directory: another run below its share would otherwise yield a free slot to that older wait, which cannot take it. At a share of 1 nothing is kept: a ticket may hold the run's one slot, and a landing waits for one to free (it goes first then, `slotTurn`). The start line says so (`landingSlotNote`). Taking a slot back from a ticket stays out (ADR 0001); `test/landing-slot-share.test.ts`.

## `src/usage.ts`

The opt-in plan usage guard (`USAGE_CHECK=1`). `usageToken(env, platform, readers, now)` is the one function that picks what a reading is made with, and `LoginReaders` (`keychain()`, `file()`) are injected so a test needs no real keychain. The guard applies only while the sandboxes spend a subscription token: `usageToken` returns `{ source: "api key" }` (the start line says the guard does not apply, no reading, no stop) whenever `ANTHROPIC_API_KEY` is set, beside `CLAUDE_CODE_OAUTH_TOKEN` or not, and `undefined` with neither, and in neither case reads the host login; a key wins over a token, as in `credentialSource`, because Claude Code spends the key first (`src/api-key.ts` then has the run ask before it bills API credits). `usageWhose` words whose plan a reading is of (the login's account, or the token's), for the start line and `doctor --verify`; the kit cannot tell whether login and token are one account. The credential, then, is the host's Claude Code login: on macOS the keychain generic password `Claude Code-credentials` (`security find-generic-password -s ... -w`), or with `CLAUDE_CONFIG_DIR` set `Claude Code-credentials-<h>`, `<h>` the first 8 hex characters of the SHA-256 of its value with a trailing slash removed (`keychainService`), as Claude Code itself names it, elsewhere `.credentials.json` under `CLAUDE_CONFIG_DIR` (else `~/.claude`); the JSON's `claudeAiOauth.accessToken` and `expiresAt` (milliseconds) are what is read. A `claude setup-token` token is inference-only and the usage endpoint answers it HTTP 403; the login's access token carries `user:profile` and gets 200. Rules it keeps: it reads on the host only, in the orchestrator, at each usage reading (`usageLine`, `usageStop`), and never refreshes (a refresh rotates the token and could sign Claude Code out), so the login's own expiry (about 8 hours) ends it - an expired login is "no reading" (fail open, asked again before the next ticket) and does not fall back, since the setup token would only get the 403 that turns the guard off for the run; a missing or unreadable login (no entry, a reader that throws, malformed JSON, no access token) falls back to `CLAUDE_CODE_OAUTH_TOKEN`; the token is never written, never added to the env the run holds, never in `sandboxEnv` or `sandboxMounts` (`src/sandbox.ts`) and never printed - `sandcastle doctor --verify` reports which source the guard would use, where it looks for the login (`loginLocation`: the keychain service's name or the credentials file's path) and the endpoint's HTTP status only. `test/usage-login.test.ts`, `test/usage-plan-applies.test.ts` and `test/usage-keychain-service.test.ts` hold it.

The plan's usage on screen is the same file's second job, and needs none of the above: no credential, no request, and it does not depend on `USAGE_CHECK`. Claude Code's stream-json output carries `rate_limit_event` lines (about three a pass) with both windows' `utilization` (a fraction) and `resetsAt` (seconds since the epoch), and every agent's raw stream is already in its `.sandcastle/logs/agent-issue-<id>-<phase>-<id>.jsonl` (`agentLogging` in `src/run.ts`). `usageFromEvent(line, at)` turns one such line into a `UsageReading` - `{ provider: "claude", windows: { fiveHour, week }, at }` with each window `{ percent, resetsAt }`, the percent a whole number from 0 to 100 - and gives none for a malformed line, another type of line or an event without both windows; the kit stamps `at` itself (seconds, when it read the line: the stream has no time of its own and an agent's clock is not the host's). The reading is keyed by `provider`, and `USAGE_READERS` holds one reader per provider, so a later provider adds one function there and the record's `usage` already names whose it is. Codex's is `usageFromCodexEvent(line, at)`, over `usageFromRateLimits(limits, at)`: a session's `token_count` event (`{"type":"event_msg","payload":{"type":"token_count","rate_limits":{"primary":{"used_percent":100.0,"window_minutes":300,"resets_at":1791188474},"secondary":{...10080...}}}}`) gives `fiveHour` and `week` by `window_minutes` (300 and 10080), never by position, `used_percent` already a percentage and `resets_at` in seconds, and none unless both windows are there. `codex exec --json` prints no `rate_limits` (its events are `thread.started`, `turn.*`, `item.*` and `error`), and the session that has them is `~/.codex/sessions/<y>/<m>/<d>/rollout-*.jsonl` inside the container (the kit runs Codex with `captureSessions: false`, so none is copied to the host's `~/.codex`, and the container takes it away), so `codexAgent` in `src/agents.ts` runs the pass's command as `<codex exec ...>; rc=$?; <CODEX_RATE_LIMITS_READOUT>; exit $rc`: the readout prints the last non-empty `rate_limits` of the newest rollout (one sandbox is one ticket's, its passes one after another) as one more stdout line, which Sandcastle's raw-line callback appends to the pass's `.jsonl` like any other, and codex's exit code stays the pass's. The readout matches unescaped JSON only, so a rollout line that merely quotes a session file (a tool result) is no reading. `test/usage-codex.test.ts` holds it, with a fake `codex` that writes the session the real one wrote (Codex 0.160.0, against a local stand-in server). `watchUsage({ logs, run, write, providers })` is the collector: while the run is live it looks every `USAGE_INTERVAL_MS` (15 s) at each `agent-issue-*.jsonl`, reads only what the file gained since the last look (an offset per file, reset when the file shrank or changed identity; a half-written line waits for its end; a line over 8 MiB is dropped, not buffered), and counts only lines after the run's own marker (`{"sandcastle":"run","run":<runId>}`, the first line `agentLogging` writes, so an earlier run's lines in a file kept across runs are not this run's). A line is read by the reader of each of `providers` (the ones the run shows). Where several files gained a reading in one look, the file written last (by modification time) holds each provider's newest; each provider's newest goes to `write` when one has come, at most once per interval (a reading that arrives sooner waits for the next look, and one that is unchanged since the last write is never written again), and `stop()` writes the last one whatever the interval says, which `burndown()` calls before it builds the closing summary. A failure to read or to write is no reading (a full disk must not fail a run). `showsPlanUsage({ apiKey, oauthToken, models })` is when a run has one: `projectApiKeySpend` says no API key is spent, `CLAUDE_CODE_OAUTH_TOKEN` is in the sandboxes' environment and at least one of the models implement, review and repair run on (the implement and review models and any ticket's `model:` override; repair uses the implementer's) is a Claude model (`isClaudeModel`: `claude-*`, or an alias Claude Code takes). `showsCodexUsage({ crossReview, apiKey, auth })` is when it has Codex's: `CROSS_REVIEW=1`, no `CODEX_API_KEY` in the sandboxes' environment, and `codexSignIn(auth)` says `plan` of the text of `~/.codex/auth.json` (`readCodexAuth`, the file `sandboxMounts` copies in; read on the host after preflight, its mode only - `auth_mode` `chatgpt`, or for an older Codex's file with no mode its tokens - and never printed): an API key, any other sign-in or no file has no plan to show. `burndown()` then writes `usage: [{ provider: "claude" }, { provider: "codex" }]`, each entry only if shown (the row says each waits for its first reading), starts the watch after the log archive with those providers and passes each reading to `run.update({ usage })`, the list with that provider's entry replaced; the record of a run that shows neither has no `usage`. `readPlanUsage` checks what a reader takes of one entry of a record (a file in a repository) and `readPlanUsages` of the whole field (a list, or the one object an older kit wrote; an entry of no known provider is left out), `usageBand` and `USAGE_AMBER`/`USAGE_RED` are the colour bands (normal below 75%, amber from 75%, red from 90%) that `status.sh` repeats in shell, and `USAGE_STALE_SECONDS` (15 minutes) is when `status.sh` greys a reading. **The guard prefers the agents' readings.** `usageStop(env, readers, agent, now)` is given the newest Claude reading of the run (`agent`: its `usage` entry) and, when it is younger than `AGENT_READING_FRESH_SECONDS` (10 minutes - as long as the endpoint's own cache), decides from it alone: no request and no credential read, the stop line naming the windows as the endpoint's reading does (`five_hour`, `seven_day`), a window whose reset has passed counted as spent no more, and `usageReadingLost()` false. Before the first reading, and once the newest is older than that, the endpoint answers exactly as before. `test/usage-pause.test.ts`.

**`sandcastle usage`** (`usageCommand(env, recorded, readers, now)`) prints the plan's usage between runs and writes nothing. `recordedUsage(logs)` gives each provider's newest reading in `logs/run.json` and the last 50 lines of `logs/history.jsonl`; a Claude reading younger than `AGENT_READING_FRESH_SECONDS` is printed with its age and nothing is asked, as the guard prefers it. Otherwise the endpoint is asked once through `usageToken`'s credential and `read` (rate-limited, so never a second time), and a failure says why, with any stale reading below it, and exits 1. `env` is `claudeCredentials(project)` (`src/sandbox.ts`: the two credentials files without `credentials()`'s checks), so an API key in use says the sandboxes spend API credits, whatever a record holds. Codex's newest reading is added with its age. `test/usage-command.test.ts`.

**`USAGE_PAUSE`** (`parseUsagePause(env, config)`: unset or empty is off, a value outside 1 to 100 is an `OperatorError` named like `USAGE_STOP`'s, from `resolveSettings` before anything runs; the project's `usagePause` is checked by `checkShape` in `src/config.ts` and the environment beats it) is the same readings acted on. `createUsagePause(threshold, ports)` is the run's controller, over the control file and a clock it is given (`standing`, `hold`, `now`): `reading(usage)` is called with every provider's newest reading as `watchUsage` writes one, and `usagePauseFor` chooses the window - of those at or above the threshold that have not reset (`resetsAt` plus `USAGE_RESUME_GRACE_SECONDS`, 60, still ahead: a stale reading says nothing of a window open again since), the one that resets last, since resuming at an earlier reset would only pause again - and holds the pause until a minute after its reset; `limit(usage, provider)` is the pipeline's `limitPause`, for an agent that hit the limit anyway (`usageLimitPauseFor`: the open window nearest to spent, the later reset on a tie, recorded at 100% whatever the last reading said, of the provider whose agent it was; nothing when no reading names an open window at `min(threshold, USAGE_RED)` percent or more - a limit message with every window well short of it is some other limit, one model's own cap, and days of waiting for the wrong window is worse than the old stop - which is also how a run on an API key, or one before its first reading, keeps stopping as it did). `source.read()` (`observe`, which `reading` and `limit` call first too, so a reading that comes in the second after a person's resume cannot write the pause again before the resume was noticed) is the schedule's pause source: it passes the control file's answer through, remembers the usage pause it has seen, and when that pause is gone before its time - a person ran `sandcastle resume` - remembers the windows then at or above the threshold by provider, window and reset time (`windowKey`) so that `reading` does not pause for them again; a pause that is gone because its time came remembers nothing, and the next window has a new reset time and pauses at the threshold as any. The controller is made only when a threshold is set, so a run without one reads the control file as before. `burndown()` prints the start line (`usagePauseLine`: `Usage pause: at 90%, resumes at the window's reset`, or that the run reads no plan usage and never pauses for it), hands `reading` each reading in `watchUsage`'s `write` (a failure there is dropped: the next reading asks again), and says each pause and resume once as the scheduler tells them (`createPauseHandling`, over injected ports for the record, keep-awake, view and log, so `test/pause-handling.test.ts` drives it with fakes). An attempt reads the pause before the guard decides (`waitOutPause`: while `paused()`, it waits at its `start` juncture holding nothing), so the guard's stop at an equal `USAGE_STOP` cannot win a race of a second against the schedule's own poll; with `USAGE_STOP` below `USAGE_PAUSE` the guard still stops the queue first, as it was told to. The setting is in `ResolvedSettings` (`usagePause`) but not in the record's `settings` group: the record says what a run is paused for in `paused`, and the status view's settings row is as it was.

The same collector carries a ticket's tokens to the status view's TOKENS column, with or without a plan to show (`burndown()` always starts the watch; `providers` is empty without one). On the same tick it counts, for each file `logOwner` names a ticket's, the `usage` of the assistant lines of this run's current pass - from the run's marker line to the next one, a message once by its id however many lines (content blocks) carry it - and hands the ticket's live figure to `liveTokenWriter` (`src/run.ts`), which writes `tokens` as the ticket's finished passes (`spent`, the results' own figures) plus the live one. A pass that returns is counted by its result and not by its log: `timed` calls `settle(issue)` in its `finally` (the watch reads what the log gained first, then stops counting every pass of that ticket so far, whatever it reads of them later), in the same synchronous step that adds the result to `spent`, so a tick can never see a pass in both. A Codex pass has no assistant lines and shows when it ends. `test/ticket-live-tokens.test.ts` holds it.

## `src/run.ts`

Preconditions, run arguments, keep-awake, preflight, prompt rendering, agent logs (with the raw `.jsonl` sidecar), run record and history, typical times and the estimate, recorded heads, outcomes (`outcomes.json`: each entry's kind from the closed set, the tickets it collided with and its line; a reader decides on the kind, never the line, and `test/outcome-kinds.test.ts` fails on one that matches the line; `test/status-contract.test.ts` holds `status.sh`'s `outcome_state` to the kinds, both ways), log archive, status pane

The run record's `paused` (`{ since, finishing }` in `mod/hooks/run-record.ts`: seconds since the epoch, and the ids of the tickets still finishing a pass, a gate run or a landing) is present while a person has the run paused (`sandcastle pause`), written by `burndown()` from the scheduler's `paused` and `resumed` changes and dropped when a stop cause is noticed (`pause stopped`), when the schedule ends or the run stops. A ticket parked at a juncture has the ticket state `paused` (group queued, word `paused`; its note says `before <phase> at <sha>`), which the report places in its working section: a run that ends while paused (stopped by any cause, which wakes the parked tickets, crashed or killed) lists such a ticket on the `Runnable now` line, with where it stood, instead of among the tickets it cut short, and the next step names it. A paused run is live (the process runs, the record has not finished), so `mod/hooks/run-live.ts` and every view treat it so. Keep-awake follows the pause: `keepAwake` remembers the inhibitor it started, `releaseAwake` ends it once a pause has nothing in flight (`finishing` empty), and `holdAwake` starts it again on the resume - only if a pause released it. `status.sh` reads `paused` for the run cell (`paused_cell`: `PAUSED since 15:40 - finishing #12 review, #14 landing` while it fits the cell, else `PAUSED since 15:40` with the tickets finishing on the second row; a green branch waiting for the landing worker reads `landing`; `since` as seconds, milliseconds or an ISO time; no end estimate) and for the queued tickets' `waits for the resume`; a `paused` that is not an object is ignored. A pause the run took for its plan's usage adds `cause: "usage"`, `provider`, `window` (`fiveHour` or `week`), `percent` and `resumesAt` (seconds since the epoch: a minute after the window's reset) to it (`UsagePaused`; the record keeps what `paused` told, a person's pause leaves them out). `paused_cell` then reads `PAUSED - weekly usage 95%, resumes Wed 06:01` (`Codex` before the window for Codex's, `5-hour` for the short one) with the tickets finishing on the row below, and in a pane too narrow for that the cause alone on the first row and `resumes Wed 06:01` on the second, shortening to `PAUSED - usage 95%` when even the window's words do not fit; a cause that is not stated with numbers is drawn as a person's pause. Keep-awake needs nothing of its own: the usage pause is told as every pause is, so the inhibitor ends once nothing is in flight and starts again on the resume.

The run record's `usage` field (`PlanUsage` in `mod/hooks/run-record.ts`) holds the plan's usage while the run shows it, a list with one entry per provider shown (`showsPlanUsage` and `showsCodexUsage` in `src/usage.ts`; an older kit wrote the one entry as an object, which every reader still takes): `{ provider: "claude" }` from the start of the agent passes, `{ provider: "codex" }` while cross-review runs on a ChatGPT plan, then each `{ provider, windows: { fiveHour, week }, at }` with each window `{ percent, resetsAt }` and `at` the seconds since the epoch at which the kit read the newest `rate_limit_event` (or Codex's `rate_limits`) of that provider across the run's agent logs. Like `demand` and `share` it is a live value, not a setting: `watchUsage` rewrites it when a newer reading has come, at most every 15 seconds, and a run that shows none (an API key and no cross-review, no Claude model and no cross-review, an older kit) leaves the field out. Readers check it (`readPlanUsages`): `status.sh` draws a line for each provider's entry for a live record only (the `claude` line none when `settings.apiKey` is true, the `codex` line none when `settings.crossReview` is false, whatever `usage` holds; the names padded to one width, a provider that has no reading yet saying it waits for one - the agent's for Claude, the cross-review's for Codex), the Herdr view sends the `sc_usage` token from it, and `gather` hands Claude's entry to the closing summary's `Plan usage at the end:` line under `Settings:` and Codex's, when it has a reading, to a `Codex plan usage at the end:` line beside it (`so far` for a live run; no Codex reading, no line).

The run record's `settings` group (`RunSettings` in `mod/hooks/run-record.ts`) holds the run's settings as one turn wrote them: `autonomy` (the level, resolved once per run), `turn` (this record's, 1-based), `cap` (the level's most turns: 1 for level 0, the level for 2 and 3, `DRAIN_CAP` for `drain`, and none for level 1, which asks after every turn), `repair` (the attempts a ticket gets after a red gate, 0 for off), `concurrency` with `asked` (the tickets at once the run takes after the machine-wide sandbox cap, and the value `--concurrency`, `CONCURRENCY` or the config asked for; the view adds `(asked N)` only when they differ), and `crossReview` (on or off, resolved once per run) with `crossReviewModel` and `crossReviewEffort`, written only when it is on, and the usage guard: `usageGuard` (was `USAGE_CHECK=1` asked for), `usageStop` (its threshold, only while it is on) and `usageReading`, and `usagePause` (the percent at which the run pauses itself for its plan, `USAGE_PAUSE`; only when it is on, drawn `● usage-pause 90%`). The reading is a fact beside the setting, never a change to it: `unavailable` when the guard's last attempt got none (`usageReadingLost()` in `src/usage.ts`: a 403, a rate limit, no token or an expired Claude Code login), written by `burndown()` after the start line and after each ticket's check, and cleared when a reading comes back - the only settings field that changes during a turn. A record without the guard's fields shows nothing about it. The cap is `poolLimit` in `src/pool.ts`, the pure form of `limit`, over the resolver's own environment and machine settings; effective concurrency is before the ticket count, so a short queue is not drawn as a clamp. The run record's top-level `concurrency` (the sandboxes at once, after the ticket count) is separate and still feeds the view's ETA and free-slot maths. The row shows `repair 1` or, greyed and dropped below 80 columns, `○ repair`, `concurrency 4` or `concurrency 6 (asked 8)`, and `● cross-review <model> <effort>` or, greyed and dropped below 80 columns, `○ cross-review`, and `● usage-guard 90%` or `○ usage-guard` (greyed, dropped below 80 columns; with no reading, `● usage-guard 90% (no reading - not guarding)` in the warning colour, which never drops); for a record that carries `crossReview`, `status.sh` drops the `cross-review` part of the models string so the models cell holds only models, and an older record's string is shown as written. `burndown()` writes it when `cli.ts` hands it a turn, and each turn's fresh record carries its own `turn`. Beside `settings`, the record keeps two live values, `demand` and `share` (the run's demand for sandbox slots and its share of the machine pool, `src/pool.ts`): `burndown()` rewrites them whenever either changes (a demand told by the scheduler, or a share that moved as another run began or ended, read every 5 seconds; the timer stops once the record is finished, `finished`), and they are no run setting, so they are not in the group. The status view's machine cell shows them as `this run  wants 4 · share 3` (with a cap, `wants 4 · share 2 · cap 2`) while the run is live (the gates queue moves to the gates row then), and while one of the run's waits for a sandbox slot is held back by its share (the record's `waitsForShare` and `waitsFor`, written by `createSlotWaits` in `src/burndown.ts`), the tickets next to start show `waits for the run's share` as their activity - as does a queued ticket whose note says so, from a kit before slot first. `waitsFor` is `share` or `landing`: the pool's wait reason (`WaitReason` in `src/pool.ts`) is `landing`, not `share`, for a wait held back by the slot kept for landing (`keptForLanding`), and the view then says `waits: slot kept to land`; `waitsForShare` stays true for both, so an older view still reads it, and a record with only the boolean reads as `share` (`test/status-landing-wait.test.ts`). An older kit's record has neither, and the view then draws the cell as before. The status view's settings row reads only these fields (`test/status-contract.test.ts` holds that), draws nothing from a record without the group, and never fills a field the record lacks. Idle, `sandcastle status` resolves the next run's settings with the same resolver and passes the group as `SANDCASTLE_SETTINGS` (`{}` when they cannot be resolved), with the whole row prefixed `next run:` (an ended run's report holds the settings it recorded, which this row is not); a bare `status.sh` falls back to the last run's record, marked `(last run)`. `status.sh`'s `settings_row` is a list of items, each with its text, a shorter text below 100 columns and the narrowest pane it stays in, so a later setting is one `set_item` call; items that do not fit the pane wrap whole onto further lines (`wrap_items`), so none is cut off.

## `container/`

Mounted read-only at `/etc/claude-code` in every sandbox (`sandboxMounts` in `src/sandbox.ts`): `managed-settings.json` registers `git-guard.sh`, a `PreToolUse` hook on the Bash, Write and Edit tools that refuses commands and writes that damage the shared `.git` (`test/git-guard.test.ts`). Managed settings sit above project settings, so a branch cannot disable it. `update-ref`, `gc`, `prune` and `stash` (whose list every worktree shares; `stash list` and `show` always pass) pass when every `git -C <path>` of the command is absolute and resolves (`rev-parse --git-common-dir`) to a common dir other than the shared one (that of the dir Claude Code started in, `CLAUDE_PROJECT_DIR`, since the shell's cwd moves with a `cd`; without it they stay refused), so a scratch repository under the temp dir is usable and a worktree of the shared repo is not; a command with no `-C` (a leading `cd` is not parsed), a relative `-C` (git resolves it from the shell's cwd at run time, which a `cd` in the same line moves), a `GIT_DIR`, `GIT_COMMON_DIR` or `GIT_WORK_TREE` assignment anywhere in the line, or a path git cannot resolve is refused (a plain quoted path is unquoted first), variable assignments before `git` do not hide it from any rule, and `push` is refused wherever it runs, since its danger is the destination. `worktree add` follows the same `-C` rule (it writes a record with the container's path into the shared `.git`, which a pass killed before its cleanup leaves behind), so a scratch repository may add one and the project may not; the refusal names `git show <base>:<path>` and `git archive <base> | tar -x -C <dir>` as the way to read the base (`test/git-guard-worktree-add.test.ts`). The file-write rule and the `rm`/`mv` rule refuse the common dir of the hook's cwd and that of `CLAUDE_PROJECT_DIR`, so a `cd` into a scratch repository or out of every repository does not let a write reach the project's shared `.git` (`test/git-guard-project-common.test.ts`). Needs bash and `jq` in the image.

The same file carries `permissions.deny` for `Monitor`, `ScheduleWakeup`, `CronCreate`, `CronDelete`, `CronList` and `RemoteTrigger` (`test/managed-settings-deny.test.ts`), and for the tools that cannot work in an unattended sandbox or that write to the shared `.git` unseen by the guard, whose matcher is Bash, Write and Edit: `EnterWorktree` and `ExitWorktree`, `Workflow`, `DesignSync` and `PushNotification` (`test/managed-settings-deny-unattended.test.ts`). A sandbox agent otherwise has Claude Code's whole tool set, and these are the ones that let it wait: a run once held a backgrounded suite for tens of minutes with `Monitor` ticks, doubling its tokens and loading the machine's shared gate slots for every other sandbox. The agent's turn is the unit of work here, so a pass that starts something long ends its turn and says what is still running. An agent may wait for a non-gate job it put in the background with one bounded foreground command (`timeout 600 bash -c 'until <check>; do sleep 5; done'`), which costs one tool call, not a tick per poll (`test/prompt-background-wait.test.ts`); nothing in a sandbox schedules a later wake-up, a recurring job or a remote run. Sandboxes run with permission prompts off (`--dangerously-skip-permissions`); a deny rule is checked before that mode and, as managed settings, outranks a branch's own settings, so it holds there. A new tool a sandbox should not have goes in this list, not in the prompts alone.

It also sets `env.BASH_DEFAULT_TIMEOUT_MS` and `BASH_MAX_TIMEOUT_MS` to 15 minutes (`test/managed-settings-env.test.ts`). Claude Code moves a Bash command that runs past its default 2-minute timeout to the background, and an agent that ran the full suite without passing a `timeout` then could not see it finish, would not claim the gates green and ended without `<promise>COMPLETE</promise>`, so the kit started a second implement session that re-checked the work and ran the suite again (about 10-17 min each, twice in one 22-ticket run). 15 minutes is above the 10 minutes (`timeout: 600000`) the prompts tell an agent to pass, so a suite run with or without an explicit `timeout` stays in the foreground; the prompts' advice stays, as the one that also works where a sandbox's settings are not these. The maximum is raised with the default because Claude Code's own maximum is 10 minutes and a default above it may be clamped to it.

Two sessions racing to one stale entry may both read, which is accepted. Set up is `.sandcastle/config.ts` being a plain file, one `stat` on the 15 s idle look, never `sandcastle doctor`; the switch is `"idleMark": false` in the personal `config.json`, read through `SETTINGS_SCRIPT` with `XDG_CONFIG_HOME` honoured as `USER_CONFIG` is, and never written - `machineSwitch` leaves the mark on for anything but `false`, and `sandcastle doctor`'s machine-wide settings check reports a value that is not a boolean. In `register.tsx` the two are drawn apart: the status line (`$.ui.status`, which Claude Code gives a warning triangle and its notice colour, neither of which a mod can change) holds only the needs-you text while a live run needs a person, and the mark is the `sandcastle.mark` state that the `AbovePrompt` band draws as one `Text` in the status view's sand (`SAND.name`) above the castle, absent while any run the band draws is alive - the session root's own or a followed one elsewhere - since a mark above a castle reads as a second, stale queue; its count is always the session root's project's. A person's choices are `/sandcastle-mark` (`markAction`, answered by a `command.run` with text and no model turn): `hide` and `show` set the hidden flag, `dismiss` records the ids of a count that is current (`choiceAfter`; a count too old to show was not seen, so it records none), `show` clears both, no argument is `markReport` (the state, the cached count and its age) and any other word is `MARK_USAGE`. The choices are one `Choice` in `$.store` under `mark:<root>`, beside `ready:<root>`: machine-local, kept across a restart, never in the repository, checked by `parseChoice`. `markText` gives no line when hidden, and no count while a dismissal holds - the current ready ids all within the dismissed ones (`dismissalEnded` is the other case: an id not in them, and an id leaving ends nothing); the idle look also clears the stored dismissal when it ends, so it is over for good, not only while the new id is ready. A hidden mark makes no queue read. A choice made while the mark is what the line shows redraws it at once (`idling`), not at the next look. `test/idle-mark.test.ts`, `test/idle-mark-choice.test.ts` and `test/idle-ready.test.ts` hold the module, `mod/tests/ready.test.ts` the count's hooks, `mod/tests/skill-turn-end.test.ts` the read at the end of the skill's turn, `mod/tests/mark.test.ts` the command's). It runs inside Claude Code, not under the kit's Node, and imports nothing from `src/`; its own imports name the `.ts` extension, so the kit's tests can import `hooks/run-state.ts` under Node too. Its own tests are `mod/tests/`, run by `claude plugin test mod`

Verifying a change to it needs Claude Code 2.1.287 or newer on PATH: `pnpm test` then runs `claude plugin validate` and the mod's own tests (`test/mod.test.ts`), and skips them without it, as CI does; the kit's own sandboxes get it from `claudeCode: "latest"` in `.sandcastle/config.ts`, since the `stable` channel is older. That checks the hooks and the tree they return, never the paint: look at a changed drawing in a real session, `claude --plugin-dir mod` from a project with a run record. The mod's API is early access, and its types are the authority, not memory. That session writes them to `mod/.claude-plugin/types/` with a `mod/tsconfig.json` (both gitignored; they are absent until then, and `mod/types/index.d.ts` holds only the band's own types); from then on `pnpm test` type-checks the mod too, which the kit's own `tsc` does not cover. Grep the types for the member you need rather than reading them: they run to thousands of lines. `claude plugin test mod` reporting "hooks modules are turned off" is Claude Code's rollout switch, not the mod.

## `site/`

The project website on GitHub Pages: static HTML, CSS and plain scripts (not modules, so it also opens from disk), no build step. `js/status.js` ports the status view's grid to play a made-up run; `js/sand.js` draws the castle, dunes and grains. `.github/workflows/pages.yml` deploys it

`scripts/version.mjs` synchronises the current release fields from `package.json`: the Herdr
manifest, site's footer and software metadata, and README release and minimum Node badges.
`pnpm version` runs it through the version hook; `pnpm version:sync` repeats it after a manual edit.
`pnpm version:check` checks those fields and the latest changelog heading without writing, as the
test suite and Pages deployment do. Pages deploys `main` on every event, so an older release cannot
restore its old copy or version; the release procedure's copy review is in `docs/releasing.md`.
